### 1.2 Can block 0 or the container grow?

- **Block 0 cannot grow in flash (INFERRED, strong).** Block 0 loads at flash 0x402C0000, payload 14,155,712 B
  + 64 B header/trailer = 0xD80000, so it ends at **0x41040000**. The `fmem` debug print gives
  `pict_addr 0x41040000` (`experiments/2026-11-08-feature-map/sections/08-connectivity-libs-blocks.md:235`,
  VERIFIED-DOC), i.e. the next flash region (pictures, not in the update file) starts on the next byte.
  All six E-PM2 versions and the E-PL5 have the same block lengths (`tools/oetool.py info` on all six files, VERIFIED).
- **It does not need to grow: block 0 already carries 1.59 MB of unused 0xFF** (1.1 above; my scan: 11 runs
  ≥ 4 KB, 1,655,197 B, `blocks.py`, VERIFIED).
- **Updater limits (VERIFIED-DOC, section 02 §1.2–1.6):** file size limit for the `E101????BIN` entry is 0x5000000
  (83.9 MB; the file is 43.3 MB); up to 32 sections; a section is written whole (header + payload) to
  `start_adrs`; checks = maker byte, model id, header copy in the trailer, 32-bit word sum = 0, length multiple
  of 16. No version check and no signature. Whether the flash writer bounds a section against a partition size
  was **not traced (UNKNOWN)**.
- **The other blocks have large blank tails (VERIFIED, `blocks.py`):**

  | Block | Blank tail | Flash address of the tail |
  |---|---|---|
  | 1 (languages/fonts, kind 0x101) | 11,126,021 B of 0x00 from payload offset 0xB43ABB to the end | 0x44783ADB–0x4521FFE0 |
  | 2 (ARTFIL grain texture, 0x106) | 130,016 B of 0xFF from offset 0x2403E0; also 0xFF from offset 8 to 0x3E0 in the directory | 0x45460400– |
  | 3 (FRAME overlays, 0x104) | 677,545 B of 0x00 from offset 0x2DA917 | 0x4575A937– |

  These bytes are in flash, not in RAM. They are a place for **data** (look banks, tables, strings), read on
  demand with the stock flash reader (§3.4). That the updater really writes the blank tail to flash, and that the
  reader accepts any address inside a block, is INFERRED (the reader is address-based; the blocks are written as
  one checksummed unit). `tools/build.py` today has only an equal-length text op for block 1.

## 2. RAM

- **DRAM size: 512 MiB, window 0x60000000–0x7FFFFFFF, uncached alias +0x40000000. INFERRED (strong).**
  Basis (`experiments/2026-11-12-hardware/03-sensor-pipeline-memory.md` §5.1, VERIFIED-DOC for the addresses):
  lowest use 0x60000000, block-0 image at 0x7E421020–0x7F1A0FE0, movie pool 0xA52B2400 + 302 MiB, buffers up to
  0xBFFFA000. Block 0 writes no SDRAM mode/timing register (the boot loader does), so there is no size constant
  to read. No memory-test routine or MMU/TLB set-up was found (grep of sections 01, 13f, 14b for
  MMU/TLB/memory test: no hit) → the MMU question is **UNKNOWN**; sibling projects report none.
- **Allocator that a patch can call: `scheap` fixed-block pools. VERIFIED** (I dumped the pool table 0x7E7348E4 and
  disassembled wrapper 0x7E507325; names from the `scheap_*_alloc: no more …` strings 0x7E734540…).

  | Pool | Base | Block × count | alloc / free | 
  |---|---|---|---|
  | small | 0x60001FC0 | 128 B × 3200 | 0x7E5072ED / 0x7E5072FB |
  | small2 (uncached) | 0xA0097FC0 | 128 × 50 | 0x7E507309 / 0x7E507317 |
  | **large** | 0x6009A540 | **16,384 B × 40** | **0x7E507325 / 0x7E507333** (116 / 133 call sites) |
  | large2 (uncached) | 0xA013AF40 | 16,384 × 27 | 0x7E507341 / 0x7E50734F |
  | middle | 0x601A7600 | 2,048 × 490 | 0x7E50735D / 0x7E50736B |
  | middle2 (uncached) | 0xA02A4080 | 2,048 × 11 | 0x7E507379 / 0x7E507387 |

  The allocators take **no size argument** (one call = one block, returned in a0); every block has a 64-byte guard
  trailer that the SCHEAPDBG task checks every 200 ticks (a write past the block ends in `Heap Destroy!` and a
  reboot). They are in segment 1 (always loaded). Peak use of the `large` pool is not measured: **UNKNOWN**
  (`sc heapshow` back-ends are compiled out).
- Other allocators (VERIFIED-DOC): image `buff` manager 0x7E576D59–0x7E579C33 (named pools PRIM/THUM/…,
  megabyte buffers), `art_buff_alloc` (art passes), FS work heap 0x7E5C8497/0x7E5C856E (≤ 512 B slots),
  OKAO W-pool 0x7E72D0BA, AVPI malloc 0x7EE8FEED, overlay-B malloc 0x7F0879CD, GUI pool 0x7ECFF1D8/0x7ECFF1E4,
  kernel memory pools 0x6041A470 (512 KB, CPU0) / 0x6049A470 (256 KB, CPU1) for task stacks.
- **Free DRAM regions (VERIFIED static only):** the 1.59 MB of unloaded gaps inside block 0's address span are RAM
  that no known load or clear writes (`docs/code-space-map.md` §2: "Write ranges, other than loads, that overlap
  block 0's runtime span: none"). The E-M10 project uses exactly such a gap as a 640 KiB plugin arena. The gap at
  the very end (0x7F14B820–0x7F1A0FE0) is suspected to be a firmware buffer on sibling bodies. No run-time check
  has been done on the E-PM2.
- A precedent for 4 bytes of patch state in `.data`/`.bss`: RAM word 0x602BE878 (an unread table entry), used by
  the interval patch, camera-tested.

### 3.2 One-call "find a file by 8.3 pattern in a directory and load it into RAM"

**0x7E5437F0(a0 = request)** — VERIFIED (disassembled; 5 callers: updater 0x7E543755 and the menu lens/flash
update functions 0x7E67EC2C, 0x7E67ECB7, 0x7E67EDE1, 0x7E67EE35).
Request as filled by 0x7E67EE35: `+0 u16 drive (0)`, `+4 → "DCOLYMP    "` (11-char directory name),
`+8 → "L???????BIN"` (pattern), `+12 destination` (0xA08F3200 there), `+16 maximum size` (0x1CA60E00 there);

returns 0 or 0xE0C. The lens-update caller runs from the Setup › Firmware menu in a normally booted camera

"load `DCOLYMP/LOOKS001.BIN` into a buffer". Field meanings beyond those five are INFERRED; whether it mounts
the card itself or relies on the mount made by its caller (0x7E67EA30 before it) is **UNKNOWN**.

## 4. The Picture Mode list

Sources: `sections/09a-art-gui.md`, `sections/09-art-filters.md`, `docs/art-filter-slots.md`,
`experiments/2026-11-09-film-portra/NOTES.md` §11, §12.2, §14.5 (all VERIFIED-DOC; several camera-confirmed).

### 4.1 Where it is

- Setting: info 111 = prm 0x9481, **one u8**, in the MODE bank (saved with Mysets). Stored values: 1 Vivid, 2 Natural,
  3 Muted, 4 Portrait, 5 Monotone (+ info 553 = 1), 6 Custom, 7 i-Enhance, 100–109 and 119, 120 = the 12 art filters.
- GUI ↔ stored conversion: mode-controller (mcon) record 0x7E84A388, composite list **raw[] 0x7E844CC0 (19 × 64 B),
  gui[] 0x7E83F70C (19 × u32)**. Info 509 and 510 (RAW-edit picture mode) have identical tables (records 0x7E84A5F4,
  0x7E84A608). Labels: u16 table 0x7EF1F4D6 (display order). Show/hide flags: 0x7E826AFC (19 pairs {gui, info}).
  API colour-tone hash 0x7EC4A864. ART-mode list: info 281, 13 bytes at 0x7E849784. ART BKT: one flag info per mode.
  EXIF: writer 0x7E70DC24 (art cases 100–120). Menu-entry → art-code: `art_GetFilterType` 0x7E71BD94 (jump table
  0x7E854A24, stored 100–120 × type 1–3) and two more copies in the live-view code (film notes §37).
- Reading a stored value that is not in raw[] shows **Watercolor**; writing a GUI value not in gui[] stores
  i-Enhance (fallbacks, 09a §1.2).

### 4.2 How the pipeline picks tables

| Stage | Normal modes (stored 1–7) | Art path (art code byte at job P+79) |
|---|---|---|
| Base gamma R/G/B, 0x7E56B790 | all take the default record; the function is not given the picture mode | hash of 32 entries at 0x7E78C154, codes 71–170 (70 after our patch) |
| Luma look curve, 0x7E56E837 | shared family 0x7E75CCF0…0x7E75D4F0 by Contrast −3…+2 plus a per-mode offset byte (0x7E763F14, **5 bytes for modes 1–5**); Portrait has its own five tables; High/Low Key have their own | jump table 0x7E78C8E4, index code − 8 (codes 8–184) |
| Saturation pair, 0x7E56DC71 | per-mode offset byte (0x7E769696, 5 bytes) + Saturation setting, 11 steps | jump table 0x7E78C514, index code − 69 |
| Six-axis records, 0x7E56D1C3 | per mode: Vivid, Muted, Portrait have records, the rest zero; four variants each | jump table 0x7E78C254, index code − 9 |
| Art matrix, 0x7E56C603 | none (B&W filter matrices only) | four compares in stock; our `matrix3` hook tests any code |
| Chroma curves, 0x7E5662D9 | default | jump table 0x7E78AEA4, index code − 69 |

**There is no per-picture-mode record table with spare indices (VERIFIED-DOC).** The normal modes are handled by
5-entry offset tables and code branches. The extensible key is the **art code** (a byte; the jump tables cover
8–184 and many codes are unused), which is what the seven film slots use.

### 4.3 Adding entries versus replacing

Replacing (done, camera-tested): the film look takes over an existing stored value and art code.

Adding a 20th+ entry needs all of these (NOTES §14.5; 09a §1–2):

1. **A stored value.** No storage change is needed: 0x9481 is a u8, and **stored values 110–118 already exist in the
   switches** — `art_GetFilterType` maps them to art codes 145, 75, 84, 69, 117, 118, 119, 151, 153, and the movie
   tables 0x7E7FF05C / 0x7E7FF008 cover them (09a Q2, VERIFIED-DOC; the emulator case `filter_type` runs this
   function). They have no GUI value. These nine ids are the cheapest "new entries"; our remap code could give
   them other art codes.
2. **The three mcon lists** (111, 509, 510): raw[] is 19 × 64 B and gui[] 19 × 4 B, packed between other lists.
   The record holds a pointer and a total size (`+4 raw`, `+8 gui`, `+12 total bytes`), so a longer copy can be
   placed in free space and the record re-pointed — the method the 240-frame patch used on record 0x7E84C5FC
   (camera-tested there). Cost for 28 entries: 3 × (28 × 68) = 5.7 KB of data if the three lists stay separate,
   1.9 KB if they share one copy (they are identical in stock).
3. **Label table** 0x7EF1F4D6 (u16 per entry, read with index 1..19 by 0x7ED3E6C5), **show-flag table** 0x7E826AFC
   (needs a settings id per entry; a new entry can reuse an always-on id — INFERRED), **colour-tone hash**
   0x7EC4A864 (an unknown value only logs an assert and shows tone NONE in rec-view), the **Picture Mode menu
   page** and Live Control / Super Control Panel lists (they read the mcon list by count — 09a Q2 — so they should
   follow it; icon strips and any fixed-size widget arrays were **not checked: UNKNOWN**), ART BKT lists, the
   art-effect switch 0x7E702A71 (jump table 0x7E826C5C on the GUI value).
4. **Labels.** Block 1 has 1,970 string ids per language with no slack between strings; new text needs a
   "rebuild language blob" tool step (not written). Reusing existing ids, or equal-length overwrites, works today.
5. **EXIF.** Values 111–118 have no art case in the writer (110 writes 15); the picture would carry a default
   ArtFilter value. New EXIF codes = a code patch.
6. **Every per-code stage** needs a handler entry for the new art code (the remap code already does this for
   listed codes), plus table space per look (below).
7. **Mysets and settings** keep working (same byte) — INFERRED.

What the interval work needed to insert one top-menu row (camera-tested): a relocated 37-row copy of the 36-row
table + 6 address loads re-pointed, the `.data` tab layout renumbered, a relocated child list, one new case in
the row-value code (51 B of code), and 31 row-number constants shifted — 48 edits, 921 B, all copied from the
E-PL6 which has the row. For Picture Mode there is **no sister firmware with a longer list to copy from**
(E-PL5/E-PL6/E-P5 lists are byte-identical, 09a Q3), so every site must be found by our own scan. Risk: the
live-view freezes of the film work came from exactly this kind of missed copy (three menu-entry→code tables).

Size of one look's tables (from `docs/art-filter-slots.md`): base gamma = 3 records × 8 variants × 512 B =
12,288 B if every variant differs (1,536 B with one table per channel; movie then falls back), look curve
512 B, matrix 18 B, six-axis 24 B (× 4 variants in stock), saturation 4 B, chroma curves 97 B. So **about 2.2 KB
per look minimum, 13 KB complete**. Seven more looks do not fit in today's 17.6 KB of data space with full
variants; they do fit if tables are read from a flash block tail or the card into RAM and the handlers point at
a RAM "active look" buffer (one 16 KB `large` heap block holds one complete look). That the image engine accepts
table pointers outside block 0 is **INFERRED** (the stock tables are themselves in DRAM; cached/uncached alias
and DMA use not checked).

## 7. UI building blocks

All VERIFIED-DOC (`sections/13d-gui-toolkit.md` §2, `15a-gui-pages.md` §2.1, intervalometer `NOTES.md` §1, §13)
unless marked; the list-page mechanics are camera-tested by the interval patches.

- **Toolkit:** a Win32-like message framework (GM_CREATE/PAINT/…, CB_ON* callbacks; message builder 0x7ECE7597,
  post 0x7ECE75C3), widget factory `Create(type, parent, resource)` 0x7ED17DB8 with 140 type ids: 15 widget
  classes 0x8001–0x8013 (0x8003 = item list / selector, 0x8010 = text label with `setText(wchar*)` 0x7ED2D510),
  drawable parts 0xC00x/0xD00x, 114 `GCPnl_*` panels. Helpers: `setVisible` 0x7EDC1851, `setListIndex` 0x7EDC1875.
  The roles of ten widget classes are not identified; **no widget was identified as a slider or bar: UNKNOWN**
  (stock screens with bars exist: WB compensation A/G, Highlight&Shadow, monitor adjust, level adjust).
- **Menu pages are data-driven.** `openPage(id)` 0x7EDCBE97 → three hash switches (0x7EFE5A14, 0x7EFE5614,
  0x7EFE4E14) → either a page getter or `getListPage(N)` 0x7EDC7DBA (registry 0x7EFE180C, 312 entries, 101
  factories). The generic list page `userCommonSecondWizard` (ctor 0x7EDC7EAA) serves 111 list ids from a
  **descriptor** found by `getListDescriptor(N)` 0x7EDFD9AF in the table 0x7F00D710 (312 × 8 B):
  `{u16 info id, u16 item count, u32, u32, u32 items}`, items of 28 B `{kind, label, …, value, guide strings}`.
  The info id ties the page to its setting: choosing a row stores the row's value. Item kind 2 = one label
  string; **kind 4 = number + unit string** (used for "1 sec … 30 sec"; 149 stock items).
- **Values:** every setting has an mcon record (505 × 20 B at 0x7E84A0B8: pointer to raw list, pointer to GUI
  list, total bytes, element size, clamp/wrap, type u8/s8/s16/u16/composite). Lists can be relocated by
  changing the record (camera-tested, 240-frame patch).
- **Top menu:** table 0x7EFFE13C (10-B rows, no slack, no count field), tab layout in `.data`, per-page child
  lists, a row-value switch in code (0x7EDEC2C0). Sub-item table 0x7EFEF4FC (196 records) for the second
  level; Custom Menu A–J table 0x7EFF7E80.
- **How the interval patch reused E-PL6 wiring:** the screens, editors, settings, defaults and texts were
  already in the E-PM2; only the row was missing, and every changed table was made byte-identical to the
  E-PL6's. A look editor has no such donor.
- **Limits found so far:** a list editor keeps its row index in a byte that is sign-extended before the × 28
  item lookup (0x7EE017BB, 0x7EE017FC) → **128 rows maximum**; the menu builder pages rows by 7; no table has
  spare rows, so anything added is a relocated copy plus re-pointed loads; new text needs a block-1 rebuild
  step; settings storage is by fixed prm tag (a new persistent setting needs a tag — reusing an existing
  unused tag such as the dormant art-filter flags is INFERRED possible, not checked).
- **What an on-camera look editor would reuse (INFERRED design, nothing tested):**
  1. *Cheapest:* a list page per parameter (descriptor + kind-4 items, e.g. −7…+7) bound to existing per-mode
     settings — the stock **Custom** picture mode already has Contrast / Sharpness / Saturation / Gradation /
     base mode (infos 205–211) and every mode has Contrast/Sharpness/Saturation (e.g. 117–119), with the stock
     Picture Mode Settings page as the editor. A hook in the table selectors can read those values. No new
     widget.
  2. The stock **Highlight&Shadow** screen (two values, live preview, spline 0x7E558466 into the luma curve) is
     an existing tone-curve editor; its panel code was not read (**UNKNOWN** how reusable).
  3. A new custom screen with bars = new panel class code in segment 3 (several KB) — needs code space first.

## 8. Emulator

`emulator` (om-emu at `~/opt/om-emu` with the local E101 model; present on this machine;
`python3 emulator/emurun.py list` ran and printed 25 cases — VERIFIED).

- **Single functions only.** No boot, no kernel, no tasks, no interrupts, no second core, no IMG engine, no
  display, no sensor, no card. RAM starts at zero and `.data` is not copied. The whole block is mapped, so
  code placed in an unloaded gap would wrongly "work" (`emulator/README.md` "Limits", VERIFIED-DOC).
- What it has been used for: table selectors (`curve_select`, `gamma_select`, `matrix_choice`, `six_handler`,
  `filter_type`, `art_kind`), menu table walkers with stubbed getters (`menu_help`, `menu_child`,
  `menu_value`, `frames_editor`), interval logic with every callee stubbed, encoder parameter functions.
- **So before a flash it can test:** the look selector hooks for every art code and stored value, a file or
  flash loader's logic with the file calls stubbed, list/descriptor walkers, and stock-versus-patched diffs.
  **It cannot test:** that a menu page draws, that live view survives, task context and blocking of file
  calls, heap exhaustion, cache effects, a changed Usr1 load, or the image result. Those need the camera.
  Misaligned accesses fault in om-emu (useful); stubbed allocators hide pool exhaustion (known trap).

## 9. Blocking unknowns

1. Does code run from the dead-3D areas, from heap RAM, and from an unloaded gap on this body (cache /
   executability)? One camera test each.
2. Usr1 load extension: size limit of the flash service 0x7E451306; whether the gap RAM is really unowned at
   run time; recovery from a boot loop has never been tested on this body.
3. From which task file calls (§3.1) or the flash read (0x7E6756B5) may be made without a freeze; what trigger
   to use (user action after boot); peak use of the `large` heap pool.
4. Whether the updater writes the blank tails of blocks 1–3 and whether the flash reader accepts those
   addresses; build tooling for blocks 1–3 beyond equal-length text.
5. Whether the image engine accepts gamma / curve tables at RAM addresses outside block 0.
6. Picture Mode list longer than 19: all fixed-size users (menu page, Live Control strip, SCP, icons, ART BKT,
   RAW-edit copies, rec-view tone) — found by scan only, no donor firmware; hidden values 110–118 untested on
   the camera.

8. Grain on colour: the Grainy Film pass 2 was not read for colour use.
9. Whether the 3D stack (579 KB) is really dead on a retail body (trace 0x7E980FC7 and the overlay-B callers).
