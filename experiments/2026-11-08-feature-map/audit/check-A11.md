## Notes on the non-CORRECT claims

**09a-57 (MINOR).** The row maps the ART BKT infos to art ids correctly: 414–423 → 100–109, 424 → 119, 469 → 120, and each info is a 0/1 flag (12 consecutive mcon records with raw [0,1]). But the "entries and order" cell says the list is "the same 12 filters". Both builders (0x7EA7633A, 0x7EA9528D) start the list with the current Picture Mode value (info 111). They then add the flagged art filters, and then the seven flagged picture modes (infos 407–413 → stored values 7, 1, 2, 3, 4, 5, 6), using the same array and counter. The list can have up to 20 entries.

**09a-68 (MINOR).** This is a header line that says the following consequences are verified from code. Most are: the Watercolor read fallback, colorTone NONE through hash 0x7EC4A864, and the Exif 110 → 15 case. But one sub-bullet openly says that the still-path acceptance was not re-traced. The `mov_art` bullet also gives only one of the two tables in 0x7E6CBFD3. The second table (0x7E7FF008), selected by bit 0 of the argument or a non-zero record word, maps 110–118 to 146/125/124/78/121/122/123/152/154 (the movie-side codes).

**09b-148 (WRONG).** The claim says that the image-engine driver range 0x7E54xxxx–0x7E56xxxx has no branch on code 118. A full scan of the range finds 51 reads of P+79 (P = desc+96). Three of them feed full jump tables keyed by the art code: 0x7E78C254 in 0x7E56D1C3, 0x7E78C514 in 0x7E56DC71 (reached from 0x7E56DD9E) and 0x7E78C8E4 in 0x7E56E837. Each table gives {118, 122} a case of its own (0x7E56D733, 0x7E56DCF8, 0x7E56E9BC). These cases load parameter tables for 118/122 only (0x7E7695AA/0x7E7695B6, 0x7E7696D8, 0x7E7606F0), so the engine does configure something specific for 118. That undercuts the "Inferred: the filter configures nothing different" line that follows. The list "96/97/165/166, 151/152 and 181–184" also misses at least 75/125, 117/121, 67/127, 155, 74/83/104/105, 70/79/102/103, 91/93, 163/164, 169/170 and 84/124. What is true: there is no literal `cmp 118` in the range, and none of the five P+79 hashes has key 118.

**10d-109 (MINOR).** The jump-table decode, the 10 table modes that are never produced and the 5 extra modes are all correct. The mode-20 sentence is wrong. 0x7E93FDBB is a two-instruction stub that returns 0. Case 20 stores that 0 as the function's return value (a2), sets d2 = 1 and never sets the edit mode d3, so the size check is skipped. Mode 20 therefore produces no edit mode, and it cannot be "the only possible source" of the 10 missing modes. Also, the "error default" is not always an error result: modes 4, 27 and 28 still return 0. Only 7, 8, 13 and 32 return 1 (second table 0x7E7CF3D4).

**10d-132 (MINOR).** The SoundCtrl getter has 39 GUI call sites in 21 GUI functions, not 20. There are 11 more sites in the sdk test shell. 0x7F0042DB is the address of the `ImportBGMProcessCallback` log string; the function that uses it is 0x7EDFA0A5. The "BGM Import" string load is right.

**10e-195 (MINOR).** 0x7E5056AC is the only instruction that stores to 0x602A9B54. But the byte lies inside the initialized-data block that boot code copies from ROM 0x7E8DA000 to RAM 0x602A9B40 (0x7E4212B8–0x7E4212E0, length 0x19314). So its initial value can be traced: it is ROM 0x7E8DA014 = 1. The card-update gate in 0x7E544A6F therefore starts closed, and 0x7E505694 must clear it (status 4 reads 0, and 0x7E45D893() ≠ 9). The same copy explains why the status-name table of 10e-34 is read at RAM 0x602A9CB4.

**15b-223 (MINOR).** The done step 0x7E53030A does not just stop. On success it writes status 0 to 0x604F943C and calls 0x7E53043E, the routine that the section calls "Abort". That routine submits one more request (+8 = 0, mode 0, done callback 0x7E53046A). The 0x6602 error code on the 4th failure is correct.
