## 15b-220 and 15b-222 (MINOR)
The step function, the reply it handles, the command it sends and the error code are all correct for both rows. Rows 0x7E530103 and 0x7E53023E are right as written. The fault is in the shared column header "error after 3 failures" and in the prose "3 tries". Every step increments 0x604F9396 on a failed reply, resubmits the same request while the count is ≤ 3, and reports the error only when the count reaches 4. That is 4 attempts and 3 retries. Each success clears the count.

## 15b-235 (WRONG)
The descriptor layout puts a tx-buffer pointer at +4, and that is false. The driver never reads +4. Send 0x7E5DC0F7 sends `length = u16 +10` bytes starting at **desc+14**, and the receive side uses u16 +12 bytes at desc+214. +14/+15 are therefore the first two bytes of the inline tx frame. Their "sync byte 0x55" / "command" reading holds for most frames, but not for the one-byte cmd-0 frame or the 0x0600 frame, where +15 is a subcode 2/3/4. +4 is an owner or context pointer: 0 for the handshake and the owner request for the 0x06/0x0600 requests, read by their callbacks 0x7E5DC7FD/0x7E5DC9F3. +0 is the completion callback, which is called with a status after tx-only completion, after rx completion and on error. 0x7E5DE8AE is the common value: it logs ` sio time out` only on non-zero status. The fields +8, +10, +12, the send 0x7E5DC0F7 and the wait 0x7E5DE91F are correct.

## 15b-243 (MINOR)
The 52-byte size (memcpy length and MEC's buffer at req+52), +0 channel, +1 type with the 0xF1 special case, +12 result buffer, +32 async callback and the completion behaviour are right. Two details are off. First, the claim states +4 = 1500 and +8 = 5 as if they were fixed values, but they are per-request parameters: 750 is the common +4 value (three builders) and 1500 appears in only one (0x7F080BEC, which has +8 = 4). Second, the "otherwise" branch of the completion also requires +40 ≠ 0. A request with neither a callback nor a sync marker is dropped without any signal.
