## Notes on non-CORRECT claims

**11-16 (MINOR).** The main assertion holds. A byte diff of v1.2 against v1.3, with the +0x80 relocation masked, leaves only the 0x7E6232ED body as a code change. That function adds the 0x7E5222E2 ≥ 0x1200 test and the six-ID list, and an ID outside the list now takes the base (+0) set where v1.2 always used +24. Besides the three version constants, the non-code changes include two build-date strings, and the row does not mention them. "lens-protocol" is a name; the evidence is only `LENS_ASKDATA_MODE_43RDSVER`-style strings, so it is inferred, but the row's "(code verified)" covers only the test itself.

**11-115 (MINOR).** Every value and address is right: d0=0, d1 13/14 (5/1), a1 0x603/0x440, builder 0x7F0A4A48/0x7F0A4A20, store at request +24, queue 0x7E5CB393/0x7E5CBA12. The only problem is the offset notation. The length and the 19/18 are adjacent stack arguments at caller (4,sp) and (8,sp), not "stack" and "stack+8".

**12-78 (MINOR).** The offsets, the names, the capture-block +60 and +336 sources and the d0 passing are all exact. Only the type label is wrong: bv_std is sign-extended (s16), not u16.

**12-213 (MINOR).** The template format, the ranges, the 445 and 85 counts, the FocusInfo start and the generic writer are all verified. What triggers the special case is wrong. The trigger is template byte_length = 0, which covers 9 tags (one of them StripByteCounts, a size). It is not "tags that hold offsets": ExifIFD, Interop and the MakerNote sub-IFD pointers carry offsets and take the generic path.

## Side finding (outside the sample)

11-version-history.md line 45 says that 1.2→1.3 is "+0x80 from 0x7E623521 to 0x7E8F1C48". The bytes show that the +0x80 shift ends at the 0xFF padding before 0x7E880000: the last non-FF byte is v1.2 0x7E87FB9B and v1.3 0x7E87FC1B. Over v1.2 0x7E880000–0x7E8F1C48 the data is at the same address: 1,201 bytes differ at shift 0 (pointers +0x80) and 43,438 at shift +0x80.
