## Notes on non-CORRECT claims

**03-92 (MINOR).** The row gives 0x7E656B1D–0x7E656F6F, about 1.1 KB, which is only the table and lookup functions at the start of the module. cam_still_func.c actually runs to about 0x7E65DA2A, about 27 KB. The file-name string is referenced as far as 0x7E65D5E7, and the error reporter 0x7E65D9A6 has 93 callers spread through 0x7E656D91–0x7E65D8DB. The cam_still_live_bulb.c row on the next line gives a full range, so this row's end bound is misleading. Correct it to 0x7E656B1D–~0x7E65DA2A.

**03-98 (MINOR).** "Takes only cmd 7 and 80" (still) and "only COM_SET" (live bulb) are true, but not at the cited addresses. 0x7E656D64 and 0x7E65DA2B are cmd-to-name lookups for the debug monitor's STL/BLB I/P printers. "…NOT SUPPORT" is the name they print for any other value, not what a rejected command returns. The real accept/reject logic is in 0x7E656EEB and 0x7E65DC34. These store 0x3C11 into the packet and report it through cam_damage's LINE variant.

**03-281 (MINOR).** The JPEG frame-resource pipeline is real: get_res_ID → resource read → JPEG header parse → decode-parameter setup. The family does not start at 0x7E721294 (that is get_res_ID). It starts at 0x7E7209BD.

**04-71 (MINOR).** The formulas and the event code 0x04070100 match the bytes. The claim leaves out two things: the 0x605B1FA2 == 1 guard, and the mode-106 branch that recomputes (552) from (96)/fps×600. "Each second" is an inference from the units, because the caller is an AVCHD callback slot.

**04-139 (MINOR).** The claim says "verified state pointers", but two of the given addresses are 5 bytes past the real entries (0x7E6EF5E2 and 0x7E6EF7F2). It also merges three states into one mid-instruction address (0x7E6EF3D6) and merges userstop_for_edit (0x7E6EF89E) into userstop. These addresses are the database's wrong function starts, not the fnNext immediates.

**04-152 (MINOR).** The strings and the function are right. The explanation ("art effects … applied to the first frame") does not hold up. The toyphoto branch tests the art-filter code (73/82 = Pin Hole), the other two branches test 0x605B0394, and "1st" matches the SIMPLE_1ST pass naming elsewhere in mov_art. This explanation should be marked inferred.
