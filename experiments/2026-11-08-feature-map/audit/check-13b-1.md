## Notes on the non-CORRECT claims

**13a-17 (MINOR).** The bounds, the art-only callers and the size of 0x7E5486B4 are all correct. The calls from outside the range come only from the six art functions that the claim names, and the two internal leaf functions with no callers are reached through function pointers in 0x7E547E5C. But the range is not only "CPU pixel kernels". 0x7E548098, 0x7E54813B and 0x7E548351 call `img_exec` 0x7E544BB5, so they submit image-engine jobs. 13a's own §3 row calls 0x7E548351 the "mask-job builder". Suggested wording: "art-only image routines (CPU kernels and engine-job builders)".

**13a-186 (MINOR).** The 512+512+3028 split, the 0x7E507325/0x7E507333 alloc/free wrappers and the MOV/REC callers are correct. But the range ends one byte into the next function: 0x7E55749A is a separate 93-byte loop function called by `mov_color_param_ready_h` 0x7E6D0C03. The free wrapper 0x7E55748C ends at 0x7E557499, so the correct range is 0x7E557410–0x7E557499. The REC caller 0x7E712703 of the free wrapper is also missing from the caller list.

**13b-16 (MINOR).** The code bounds are exact, the `ff ff` and BASIC table are present, and the four addresses in the 0x7F069000 "data" page are code with the callers that the claim gives. But the rodata column names only the two 3-byte constants of F076. The library also uses eight direction-offset tables at 0x7F06ACD4–0x7F06AD93 and a u16 quarter-sine table at 0x7F06AD9C–0x7F06ADC1. The sine table is used by the angle helpers 0x7F068F9C/0x7F069020, which the claim itself includes.

**13b-18 (MINOR).** The AVPI start (0x7EE8F4F4, which calls the kernel service 0x7E431316), the AVPI end (`ret` at 0x7EECE316, then OSD-debug strings) and the result of the caller scan are all correct. Three details are off. (1) The lower bound 0x7EE63000 is in the middle of function 0x7EE62F80, which ends at 0x7EE63004. That function, like 16 other functions in the "C3D API" span, is itself called from inside 0x7EE63000–0x7EE8F4F3. So the two spans are one mutually linked C3D library, and the boundary is a page number, not a function boundary. (2) "Codec tables 0x7F0327DA–0x7F033xxx" is not verified: nothing loads 0x7F0327DA directly, the codec driver's table immediates start at 0x7F031DEC, and 13b item 12 labels the role of 0x7F0327DA+ as inferred. (3) "0x7EE61A–0x7EE62F" is a truncated address form. The real span is 0x7EE61A0A–0x7EE62F80.

## Side finding (outside the sample)

13b §2.3 says that 0x7F066812 makes a "101-bin luma histogram of {ΣB, ΣG, ΣR, n}". The bin index is in fact 100·p[0]/(p0+p1+p2), which is the byte-0 (B) ratio, at 0x7F0669EE–0x7F066A07. Luma (19595/38470/7471) is used only as a filter: pixels whose luma is at or above the luma of the reference colour are skipped (0x7F06696E–0x7F066986). The size 1616 = 101 × 16 is correct.
