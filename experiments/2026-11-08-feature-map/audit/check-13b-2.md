## Notes on non-CORRECT claims

**13c-11 (MINOR).** The A4 correction moved the end to the first function that has a TraShareTakeStatus string, but the package starts 9 functions earlier. 0x7E9698EC logs `clearIntervalShootingState state[0x%08X]`; its string is directly before the `getIntervalShootingState` string in rodata. It uses the same lock as the `TraShareTakeStatus.cpp` assert functions. The RAM block 0x602B0CB4–0x602B0D18 is used only from 0x7E9698EC upwards. The start 0x7E966000 is a round number inside a shell helper. The first 2.6 KB of the row is user-shell support code; HIGHLEVEL_MAIN code starts at 0x7E966A17. Both the corrected end (A4 2026-11-09) and the start are wrong, but every named part of the row is inside it.

**13c-14 (MINOR).** The "strings" basis covers only 0x7EB7FE18–0x7EB80016. From 0x7EB81100 to 0x7EB84344, no data words point to functions; all of them are called from inside the class. 0x7EB84345 is a different kind of code: a 4 KB static function called by the APP_EVENT receiver, which works on globals and not on `this`. The getters 0x7EB85374 and the logger call at 0x7EB8552A that loads `Com_EvSenderManager buffer overflow!` link it to the 6-entry event buffer at 0x602B48BC. The class row should end at 0x7EB84344, and the Com_ row should start at 0x7EB84345.

**13c-18 (MINOR).** The listed contents are correct, but the list starts too late. The first ~1.7 KB (0x7EBA0AA9–0x7EBA1187) is a face-information device that the list does not name. The table in §5.4 also leaves it out. The 84 bytes after 0x7EBA4867 are helpers of the picture-file-creation device (call edges), so the Dev/OXF boundary is 0x7EBA48BB/0x7EBA48BC. The OXF row has the same 84-byte error.

**13c-20 (MINOR).** The main assertions (bounds, string-less shape, the four FACE call sites, OKAO-area callees) are correct. The added sentence "Error codes 0x0CA000xx" is false, and 13b §2.2 contradicts it: 0x0CA00080 is the Smart Skin handle magic. The return codes are small negative numbers. The soft-float range is also given too narrowly: the callees span 0x7E4FE9D7–0x7E5019E4, and they include memcpy/memset.

**13c-140 (MINOR).** "Verified call" is correct for 0x7EB86C21 → 11772. The described meaning covers only one of its two callers. The lookup-and-ack path 0x7EB868A6 sends 11772 to a requester that is already registered. 0x7E96E40A sends 11772 on a third path. So 11772 is a general "acknowledge to requester" event, not a registration-only one. The name "ack" is still inferred.

**13d-14 (MINOR).** The A4 correction is right about the 0xFF padding after 0x7ECB1003. But the ramp tables stop at about 0x7ECB083B, and the 2 KB before the `retf` is a 19-word pointer table followed by more 0xFF. The pointer table is worth adding: it points to 19 0-caller functions that construct globals, probably the static-constructor list. Also, the region boundary 0x7ECA1020 is inside a ramp that starts earlier. 13b gives the OKAO Smart Skin LUTs as 0x7EC92318–0x7ECAFF3C, which covers most of these "ramp" bytes, so "role inferred" understates what is known.

**13d-23 (MINOR).** Only the end is off. 0x7ED86DA0 is the entry of the last SS_COMMON handler (EVT_REQ_REC_DISP_CURSOR, returns 516), so the row cuts that handler to one byte. The inclusive end is 0x7ED86DA5.

**13d-64 (MINOR).** "Scale each child rect" is not what the code does. In all 61 builders, the factors multiply only x1 and y1. The builder computes w and h first, then sets x2/y2 from the new origin, so the size stays the same. The effect is that child positions are remapped and child sizes are not. That weakens the inferred "rescale layouts for HDMI/EVF" reading: it fits a relocation better than a rescale. The cited 0x7ED37E90 is an instruction address inside 0x7ED37E2D.

**13d-125 (MINOR).** Most helpers are correct. Four details are wrong. 0x7EDC181B is "set text by id, or hide if the id is 0", not "+ show". 0x7EDC1972 uses vt+48 to read the rect. 0x7EDC189F does not compare before it sets. The range end 0x7EDC2000 is inside the 1,333-byte fn 0x7EDC1B37.

**13d-156 (MINOR).** The A4 correction fixed the majority pattern, which is correct (93/115). It miscounted the variants: 16 + 1 (not 17) for the no-tail-call forms, and 4 different child-array offsets (+796, +808, +824, +888) instead of "4 from +796".
