## Notes on non-CORRECT claims

**11-19 (MINOR).** The widening, the new helper 0x7E626BD4 with 39 call sites, and the struct growth all check out. One of the 39 sites clamps to [0, 32767], not [−32768, 32767]. Every site uses hi = 32767, so §7's "21 with hi = 32767" is also wrong. The +0x2AC shift covers only the code from 0x7E626937 to about 0x7E76EA1F. The data after it moves by other amounts, and the code from 0x7E8F1C68 on does not move. "Focus-position" is a name taken from the `fcs_*` context, but the claim states it as code fact.

**11-31 (MINOR).** The split/merge finding is correct, but the code is not byte-identical. Seven call displacements in the two functions change by +0x80 because their callees moved.

**11-85 (MINOR).** The new strings are real. 0x7E458938 is not a debug command. It is a periodic I²C health check with a 10-try life counter that disables the device when the counter runs out. That is a runtime change in v1.2 and is worth listing. 0x7E458B28 is the ACC shell command, which already existed in v1.1 (0x7E458AAB). v1.2 only adds `rreset`, `rdump` and `Who am I?:` to it. From its x/y/z offset tables at 0/90/270°, "ACC" looks like an accelerometer, but that is inferred.

**11-112 (MINOR).** The mechanism holds: the value goes to stack slot (8,sp) and is stored at request +24, then the request is submitted. But the addresses 0x7F0A4A20 and 0x7E5CBA12 are the v1.5/v1.6 ones. In v1.3/v1.4, where the change happens, they are 0x7F0A4A48 and 0x7E5CB393.

**11-119 (WRONG).** The classifier's conditions are stated wrongly. The helpers return 1 when lens-ID byte1 **= 0**, not ≠ 0. The gate is bit 0 (mask 1) of +6632, not bit 1. With byte1 being the high byte of the 16-bit make, the corrected test means make = 0 → 1, and make = 2 or 3 → 2. That fits the ExifTool inference; the claimed version would almost never return 1 or 2.

**11-120 (MINOR).** The gating change is right. The v1.4 address is wrong (0x604F7F60 in v1.4; the record moved by 4 bytes), and the bit is bit 0, not bit 1. The name "Lens-OIS state test" is presented as verified but has no support. The code uses this test to choose between Panasonic-private and Olympus-private lens-info pages, so it looks like a "Panasonic private-protocol lens" test.

**11-121 (MINOR).** The v1.4 → v1.5 pairing is right: v1.4 computes the value inline in 0x7E5A6535 for +3860. v1.5 adds 0x7E5A59EA/0x7E5A5A5A, a new byte +735 (the old +735 moved to +736) and a copy into +3860. 0x7E598A72 is used in both branches. The difference between them is only that with `is_type` = 1 the earlier value is kept when it is not 0.

**11-127 (WRONG).** The overlay diff contains one functional change, and the claim misses it: the handler for SetDevicePropValue(0xD406) was stubbed. v1.4 copied the host's string into RAM, bounded only by the 8-bit length. v1.5 accepts it and discards it. The changed call operands in `SetDevicePropValue` are only a side effect of that. 0xD406 is MTP's Session Initiator Version Info, which Windows sends when it connects (outside knowledge, inferred). So "Windows 10 not found / probably host-side" is not supported. This change is the best candidate for the Windows 10 fix.

**11-137 (MINOR).** "Not ≈ relocation" and "about 300 in AF" hold. The count of 358 "code functions" includes about 60 non-AF entries. Most of them are data decoded as code or boundary splits. Outside the AF range, real code changes are four constants.
