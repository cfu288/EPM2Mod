## Non-CORRECT claims

**09a-12 (MINOR).** Everything the claim states about the table is true: 505 × 20-byte records at 0x7E84A0B8, built by 0x7E7077D3 (loop bound 505) into a 128-bucket hash at 0x605B9750, and looked up by 0x7E70782A. The field meanings also match the data. The flaw is the evidence. The four users named do not read +2, +16 or the type codes 2–5. 0x7E7070B4 even treats types 1 and 2 alike (both `movbu`, no sign extension). Those fields are shown by other code, which 13e §3.1 cites: 0x7E707854 matches +2, the u8 step 0x7E7074B5 uses the clamp argument, and the dispatcher 0x7E70761C has cases 1–6, with `extb` for type 2. Fix: cite those functions for +2, +16 and the type enum.

**09a-68 (MINOR).** The bullet list under this heading says that a stored value 110–118 gets no art entry in Exif. That is true for 111–118. It is false for 110. The E-PM2 writer 0x7E70DC24 has a real case for 110 at 0x7E70DE4B: `mov 15,d0; movhu d0,(a3); mov 1280,d0; movhu d0,(2,a3)`, the same pattern as the shipped filters. ExifTool names 15 "Pale & Light Color II". The E-P5 writer does the same (0x7E3ECFAA). This also contradicts the 09 §3 table row for 110 ("case, no value written"). That row was not sampled, but it should be fixed too. The other consequences (Watercolor read-back, colorTone NONE + assert, mov_art codes) were re-verified.

**09a-78 (WRONG).** The claim relies on the 07-settings.tsv counts. Those are right for direct prm sets (0) and Set_CameraInfo (0). They are wrong for GUI setSetting. The setSetting wrapper 0x7EE01D4E (it logs `setSetting Mode=%d Val=%d`) is called with constant id 111 at 0x7EDE26EC (value from a table at 0x7EFF63EC) and at 0x7EE00E6F/0x7EE00E75 (value 8 = Pop Art, or 1 = Natural). Also, `Set_CameraInfo_Simple` 0x7E6FCC72 is called with 111 at 0x7EA807AC (`loadOwbShootingPrevState` restore), 0x7EA817F6 and 0x7EA81823 (value 1). The mcon setter 0x7E6FEAE0 is called with 111 at 0x7E704036 (the 09a §1.3 reset hook). Every one of these goes through the mcon GUI→raw conversion, so the conclusion that the GUI cannot store 110–118 stands. The sentence "no constant-id writes" and the 0-setSetting count do not.

**09b-76 (MINOR).** The acceptance facts are right: 151/153 appear only in the req+2 == 3 block 0x7E71C1BA. But 0x7E71C0E1 is `art_chk_type_rec`. Its trace id 7 maps to that name in the {id, name} table at 0x7E854824. `art_chk_type` is its caller 0x7E71C075 (trace id 6), which sends req+2 1..6 to 0x7E71C0E1 and 7..9 to `art_chk_type_mov` 0x7E71C28B. 09-96 names it correctly, so 09b contradicts 09. Also note that "rejected" is not final. When this helper returns 1, art_IsSupportType 0x7E71BC93 runs `art_chk_effect` 0x7E71C4DC, which returns 0 (supported) if any effect slot (req+8..16) is set and the processing type matches.

**09b-161 (WRONG).** The claim says the only other `cmp 108` sites are 0x7E551E93 and 0x7F0A3479. In fact there are 40 sites in the function disassembly and 93 in the linear sweep. Some are in the REC art code, where 108 is the picture-mode **menu id** Gentle Sepia: 0x7E70E5BD in `rec_art_set_ctrl_nr` (104/108), 0x7E7160C3 (104/108/109), 0x7E70C674 in `rec_3d_lens_set_ctrl` (5/108), 0x7E71822D in `REC NR stl2nr` (5/108), and in both ART BKT builders (0x7EA764C5, 0x7EA9540C). Others are unrelated (for example a shell parser at 0x7E6E3E85 that compares the character 'l'). None of these tells art code 108 apart from 73/106, so the Pin Hole III conclusion survives. The search-completeness statement is false, and so is "(verified)".

**10-39 (MINOR).** The effect-value table starts at 0x7EFE866C, not 0x7EFE8664. The bytes are 12-byte records {u16 value, u16 label, icon, icon, help, 0}. 0x7EFE8664 is inside record 0x7EFE8660 (value 3, label 791 "Filter Type III"), the last row of the Filter Type list that starts at 0x7EFE8648. The GUI code loads 0x7EFE866C (0x7EDD57C3, 0x7EDD5D77, 0x7EDD6FF1). Nothing references 0x7EFE8664. The value ↔ label pairs and the one-hot output in 0x7E702A71 are correct. 10b §6 uses the same wrong address. A small wording point: "Active (verified)" covers selection only. 10b itself says the step from setting to `art_effect_*` module was not traced.

**10a-59 (MINOR).** The page/panel factory 0x7EDCBE97 has two hashes: a 256-slot {id, handler} hash at 0x7EFE5A14 (ids 1..651) and a 128-slot hash at 0x7EFE5614 (key = id−16, ids 17..606). Panel 637 is at 0x7EFE5E04 in the first one. Its handler 0x7EDCBF28 calls 0x7EDE1E3D, as claimed (37 other ids share that case, among them 15 and 629). 0x7EFE5814 is neither table's base; it is slot 64 of the second hash (key 448).

**10a-118 (MINOR).** The HDR top-menu row (id 472, label "HDR") is present in all four bodies. It sits in the same 12-byte-row table between Bracketing (605) and Multiple Exposure (267). But `MODE_HDR1_HDR2_JUDGE_NG` is only in the E-M10 block 0. The E-PL7, E-M5 II and PEN-F contain `CHECK_IS_NOT_HDR1_HDR2` instead, and no body before the E-M10 has either string. The cited addresses 0x7E5B1CA6 and 0x7E5DAACE are the label halfwords at row+10. The rows start at 0x7E5B1C9C and 0x7E5DAAC4.

**10a-144 (MINOR).** All the setting facts are right: panel 629's children, the three mcon lists, and drive entries GUI 24/25 with info 0 = 5. The string `KIND_CUSTOM_INTERVAL` is at 0x7EC52F5A. 0x7EA981DB is the function `startSelfTimer`, which picks `KIND_CUSTOM_INTERVAL` or `KIND_NORMAL` after a vtable test (0x7EA981F7). The units of 474 (0.1 s) remain inferred, as the claim says.
