## Non-CORRECT claims

**10c-171 (MINOR).** The conclusion holds: no GUI path stores 110–118 in 0x9481. The cited evidence is misstated. Infos 509/510 have the same 19-entry lists, with art values 100–109, 119 and 120, and plenty of other lists hold numbers in 100–120. The correct statement: 0x9481 maps only from info 111 (table 0x7E7C95B4), and the only composite that lists info 111 is {111, 553} at 0x7E8186D6. Its 19 raw values contain none of 110–118. Across all 505 records, 110–118 appear only as scene codes (infos 19/24/26/280, composite 2340).

**10d-109 (WRONG).** Decoding all 33 words of the jump table 0x7E7CF458 gives these results:
- API modes 4, 7, 8, 13, 27, 28, 29 and 32 fall to the error default.
- Mode 18 maps to 16 and skips the second size check.
- Mode 20 calls 0x7E93FDBB instead of loading a constant.
- The constants produced are 1, 2, 7, 8, 10, 11, 12, 14, 16, 0x81, 0x82, 0x83, 0x84, 0x85, 0x87, 0x88, 0x89 and 0x8A.

So the size check does not "know every mode". Ten of the 23 modes in 0x7EBB8D88 are never passed (0x80, 0x86, 0x8B, 0x8C, 0x8F, 0x90, 0x91, 0x92, 0x93 and 0x94). Only the narrower claim, that 0x85 is known (mode 6), is true.

**10e-34 (MINOR).** The table content is right. The end bound should be 0x7E8DA334 (exclusive). The final eight records are a separate mode-name list with colliding ids (4 = " M "). This matters for any reading of "status 4" (see 10e-195).

**10e-87 (WRONG).** The text joins two different ADJ operations:
- **Reads:** the status reads 0x1706–0x170C (all seven, not five) are in op **0x9005**'s status builder 0x7F08056A (0x7F080519 ← 0x7F08034A). Op 0x902A's handler 0x7F0803BD → 0x7F082C09 reads none of them.
- **Print:** `cube is disable` is printed only indirectly, by the cube routine 0x7E8FED1A, which 0x902A's sub-op 0x7F083BDD calls.
- **Location:** 0x7F080B39–0x7F080BC2 is a run of status reads inside a linear packet builder, not case code. Section 01's table (0x9005 → 0x7F080519 → 0x7F08056A) and section 08's table (0x902A → 0x7F082C09) were right. The L1 relocation of this sentence made it wrong.

**10e-127 (MINOR).** The record at 0x7EFFE1DC is verified. The statement that it is in the Playback tab is inferred: there is no tab marker in the record, and 07 §3.1 labels the split as inferred. The neighbouring rows (Edit, Print Order, Reset Protect) make the inference strong, but it must not be labelled verified.

**10e-195 (MINOR).** The gate compares `table[poweron_factor]` (0x7E73522C), not the factor itself. Section 02 §1.1 says this correctly. The values are not fully "undecoded": 12 = "Powr", and the table also yields 0x1506 "MdaC", 0x400 "UsbC" and 0x121C "LpSw". Two further points:
- **Writer:** 0x7E505694 is the only writer of 0x602A9B54, and it can only clear the byte. If the byte starts at 0, the OK-key condition has no effect. The initial value is not traced.
- **Duplicate id:** "status 4 = O  k" ignores the second id-4 name " M " in the same array.

**10f-77 (MINOR).** The table is identical in all 8 bodies, E-PL6 (0x7F0D3C5E) included. Each body has 4 identical copies. The list names 6 other bodies and says "7".

**10f-104 (MINOR).** The gate logic and the id → tag mapping are right. The prm store has a CSV-override layer that is consulted before every class: request kind 2 → 0x7E4564D8 → 0x7E45722C sets 0x603A0E34 = 1 and builds the index at 0x603A8E38. One source of that request is the card file `PARAMDT/CP??????CSV` (0x7E5B108F, reached from 0x7E5B0C1A). So "the arg ≠ 0 path can never pass on the E-PM2" holds only while no override is loaded. Write it as "cannot pass from ROM defaults; an override (card CSV, ADJ) is not ruled out".

**10f-124 (MINOR).** I decoded SS_MENU_MAIN (0x7EFD40C4: 12 states, 71 events, 211 handlers), column state 6:
- Up = 0x7EDAB963 sets the counter to **0**.
- The counting steps are Down → Left → Right → 1st release → 2nd release (0→1→2→3→7→8), then OK at 8 → 0x0A01.

Pressing Up first does no harm, because it only resets to 0, but it is not a step. 13d §4.3's own aside, "0x7EDAB980 is the Down step", contradicts its sequence. The key-code test `cmp 4` is in 0x7EDFD624, which also needs (188,a0) = 1, not in 0x7EDFD665. 0x7EDFD665 itself calls getShippingInfo(4) via vt+12, posts 0x9628 through 0x7EDC5BF5 and then calls `0x7EDC5C47(11, 11)`.
