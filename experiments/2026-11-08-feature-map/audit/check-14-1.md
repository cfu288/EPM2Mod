## Notes on the non-CORRECT claims

**14a-15.** All the boundary facts are confirmed. The previous function ends at 0x7EE02094, the 672 functions run from 0x7EE02095 to 0x7EE294B4, and the init has a single caller. 0x7EE2946D is correctly described as the *body* of `glPointSize`: the table entry for `glPointSize` is 0x7EE29468, a 5-byte prologue that falls into 0x7EE2946D, and `glPointSizex` 0x7EE29449 calls it. The only error is the word "loads". The 1,055 references to 0x602BE994 include two stores (0x7EE11BDB, 0x7EE133AA), so the correct figures are 1,053 loads and 2 stores, all in 0x7EE026DC–0x7EE2946F.

**14a-16.** The release 0x7EE47412 has 180 call sites. 156 are inside the engine core and 24 (in 19 functions) are in C3D, so "20 C3D call sites" is a wrong count. The type table 0x7F02AA14 is referenced only by 6 `mov imm32` in the engine (0x7EE47373–0x7EE47AD2), so the "used only here" part is correct.

**14b-32.** cam_mirror code does not stop at 0x7E6437F1. Two more `mirror_dummy_post_*_err` functions follow, 0x7E643871 and 0x7E6438E9, and the second one calls the MI_RES function 0x7E642FAE. The last function to place in mirror is 0x7E6438E9, which ends at 0x7E643932 (the modules.tsv proposal `7e642325 7e6437f1` at line 232 should read `7e642325 7e6438e9`). The "mirror" identity is verified (`MI_*`, `(cam mirror)`). The file name `cam_mirror.c` is inferred, not read.

**14b-144 / 14b-151.** The code facts in both headings are verified: the cam_list functions, their callers and the 0x28 helper, and the cam_mem range and its boundaries. The problem is the label. "(V)" covers the file names `cam_list.c` and `cam_mem.c`, which do not occur in the E-PM2 bytes and come from the alphabetical-order rule. The same section's table already says "name I" for both. The bullet labels should say "V code; name I".

**14b-177.** The locks, refcounted open/close, submit, jump table, error code, name decoding, MAG START callback chain, F006, the done callback's lock release and `+16` call, the printer and the shell strings are all confirmed. Two details are off. (1) The handlers are not in code order. In the jump table, codes 6–9 and 16 go to 0x7E518271, 0x7E517E81, 0x7E518123, 0x7E517FCF and 0x7E5183C5, so in address order they run 7, 9, 8, 6, 16. The unnamed MOT code 6 has its own handler, 0x7E518271. (2) The range end 0x7E518BBA is a function start, and the layer's state 0x604F63A0 is used by 0x7E518BCE and 0x7E518BF2 after it, so the layer extends to at least 0x7E518C61. A smaller point: "class = byte +9" is read by the printer (`(+8) & 0xFF00`), not by the submit, which dispatches on the code alone.
