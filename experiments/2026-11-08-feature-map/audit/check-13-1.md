## Paragraphs on non-CORRECT claims

**13a-166 (WRONG).** 0x7E544AA9 does not create kernel objects 102 and 105–108. It calls 0x7E463C8E(n, 5, handler), which packs {5, handler} and calls 0x7E44B57F. That function rejects n ≥ 125 with `!!Wrong IRQ Number`. It then writes the interrupt-control word at 0x99200000+4n (0x99300000 on CPU1) and stores the handler in a per-IRQ table. So 102 and 105–108 are IRQ lines, and 0x7E5451CB… are their ISRs (each calls 0x7E54D815 and sets an IMG_END flag). For 107 and 108 the function also calls 0x7E44B5E7, which zeroes the same control register. Separately, the "IMG_END flag create" 0x7E55EB2D only calls 0x7E449000 = `clr d0; retf`. The flags are therefore not created here; they must exist statically. The caller (Usr0), the buffer init 0x7E54D59A and the two task starts (0x7E449541 `OlyTaSt`) are correct.

**13a-175 (MINOR).** The dispatch and table address are verified. The label "colour/tone parameter handlers" is inferred, but the row is marked V. Change it to "op-type parameter-block handlers (role inferred)", or move the label out of the V basis.

**13a-189 (WRONG).** The bit-depth switch at 0x7E55ED32 picks one of three 16-entry tables: 0x7E789230 (byte access, default), 0x7E789270 (12-bit packed: kernels such as 0x7E55F1EA read pixels through 0x7E55F524, 10 pixels per 16 bytes) and 0x7E7892B0 (halfword access). Every table's slot 15 is an empty `retf`: 0x7E55F1E7, 0x7E55F521 and **0x7E55F97A**; the database folds the third one into 0x7E55F959. The slot index is built in 0x7E55EF52 as a 4-bit mask of missing neighbours (x<2 → 4, x+3>w → 1, y<2 → 2, y+3>h → 8, ORed into (30,a0)). The 4-neighbour mean is therefore the slot-0 case only. Correct text: "three 16-slot tables for 8-bit (0x7E789230), 12-bit packed (0x7E789270) and 16-bit (0x7E7892B0) data. Each has 15 kernels and one empty stub (0x7E55F1E7, 0x7E55F521, 0x7E55F97A). Depths 9/10/14 log an error." The prm list (0x70C4/0x7044/0x7144/0x7052 under flag bit 0x1; 0x70D4/0x7084/–/0x7092 under 0x2), the iterator and the callers are verified.

**13a-196 (WRONG).** IMG0_LOCAL (CPU0 task, table entry at 0x7E438DBC) does not execute the job. 0x7E575E13 has zero callees and only copies: 196 bytes of the job to 0xA07500BC, then the +100/+96 sub-blocks into 0xA0750120…, with pointer fix-ups. The task then sends {0xA07500BC} to mailbox 0x7E43EE94, which the CPU1 task 0x7E575DB8 (cfg 0x900F) receives. That task runs `img_exec` 0x7E544BB5 and replies on 0x7E43EE96. Only then does IMG0_LOCAL copy that result into the reply and send it on 0x7E43ECBA. Correct text: "IMG0_LOCAL: receive job → marshal it into shared RAM (0x7E575E13) → forward it to the CPU1 twin 0x7E575DB8, which executes it through img_exec → relay the twin's result". The mailbox reading of 0x7E436467/0x7E434C5C fits the call pattern (pointer messages with an 8-byte header), but it is inferred.

**13b-42 (MINOR).** The names are right, and both functions clear the 4-word descriptors (0x602AE508–514 and 0x602AE518–524). But neither Free can fail, because each returns 0 unconditionally. The caller's FreeB check also re-tests the FreeW result in d2. "Prints these strings when they fail" therefore describes dead code, and the FreeB print is tied to the wrong result. The name evidence is the string order next to the call order, not an observed failure print.

Notes on CORRECT claims with caveats: 13a-179 uses a range end that is the start of the last function; 13b-41 omits the "already initialised → −1" case; 13b-208 and 13b-242 contain inferred labels ("contour", "eye-retouch", "FD engine") that the claim text does not mark as inferred everywhere.
