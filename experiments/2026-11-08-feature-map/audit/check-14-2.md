## Non-CORRECT claims

**14c-98 (MINOR).** The path is right: 0x7E880EFF → 0x7E880F0C → appevent queue → HLS_EVENT 0x7E96DD58 → sender 0x7EB84345 (return 1 = consumed) → 0x7E96DE42 (EVFW). Four details are off. (1) The "118 callers" are 118 call sites in 76 functions. (2) A pre-filter, 0x7E96DB39, runs before the sender and can skip the event. (3) Only codes with the top nibble 0xF are kept in the backup list (0x7E96DE2F, then 0x7E96DFFC, then `NOT FOUND EVFW BACKUP`). Any other unmatched code is only logged as `NOT FOUND EVFW`. (4) `EVFW FROM BACKUP` belongs to the replay function 0x7E96DF97 (caller 0x7E96DAA3), not to the forwarding function.

**14c-134 (WRONG).** The module bounds and four of the five members are correct. The teardown helper 0x7EA17103 is wrong. It is called only by the dtor 0x7EA10E9A, which is slot 0 of vtable 0x7EC2AA78. That vtable belongs to the 1,180-byte singleton class whose getter, 0x7EA10D3E, starts one byte after the claimed MediaInfo end. CapMed_MediaInfo's vtable is 0x7EC2A708, and its dtor is 0x7EA10563. 0x7EA10563 destroys the members at +352 and +112 and calls the base dtor. It never calls 0x7EA17103. F033 belongs to the next class (the CapMed_MediaController/MediaManager object, name inferred), not to MediaInfo.

**14c-143 (MINOR).** The mechanism, the 22 initialisers, the 21 single dispatchers, the 77-record example and all the listed tables check out. Three details are off. (1) The C++ ctor table that the walker uses is 0x7F033AC8–0x7F033B7B (45 entries; walker id 3, size 180, which agrees with 14d §1). 0x7F033AC4 is a vtable slot. (2) One of the 22 initialisers, 0x7ED9855F, writes a null `{0, 0}` record, not `{−1, method}`. (3) The dispatcher does not clear its output fields. It first reads data-model values into them.

**14c-144 (MINOR).** The record index is wrong. The Live Bulb record at 0x602BC278 (= 0x7ED9C8FB) is record 65 (0-based) of the table at 0x602BC070, not record 49. Record 49 is at 0x602BC1F8 and holds 0x7ED9B8BD. The API, the getters, the u16 at 0x605178BE and info 696 → prm 0xD721 are all correct.

**14c-145 (WRONG).** Everything is correct up to `api_rec_Update_Bulb_Lv` → TAKE_MAIN message 19. The TAKE step is wrong. The TAKE dispatcher 0x7E58204D has two tables per state. For StlLiveTake (state 0x10, descriptor 0x7E7909A0), mbf messages use 0x7E790050 and flag events use 0x7E7900A0. The cited 0x7E790060 is in the middle of the message table, and that table has none of the events listed. Message 19 matches its record {0x13, 0x7E5A2A27}, which sends request 268 through 0x7E5A8632. The records 0x38 → 0x7E5A2C01, 0x1B/0x1C → 0x7E5A2A6F and 0x1D → 0x7E5A2B4C are in the event table 0x7E7900A0, and the event path delivers them, not message 19. That event 0x38 is the reply to request 268 is a reasonable reading, but it is inferred. The handler behaviour as described is correct. A smaller point: the GUI table does not start at 0x7EEDE0C0 (records start at least at 0x7EEDDEF0), and the second field is not always 1.
