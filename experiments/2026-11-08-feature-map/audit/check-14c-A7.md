## Non-CORRECT claims

**14c-12 (MINOR).** The row's start comes from the old scope of section 06 ("about 0x7E966000"). 0x7E966000 is inside 0x7E965FD1, a function of the debug-monitor formatter group. The first ~2.6 KB of the stated range (0x7E966000–0x7E966A16, 19 functions) is the printf-style formatter 0x7E966355 and its helpers. These serve the monitor commands at 0x7E963xxx–0x7E965xxx, not HIGHLEVEL_MAIN. The HIGHLEVEL_MAIN code starts at 0x7E966A17 (task entry 0x7E966A78), as 13c line 12 already says. The rest of the row is correct: the end 0x7E9698EB, the HLS wrapper example 0x7E96985A (kernel 0x7E44B36F/0x7E44B390), the logger and the growable array (0x7E966C01).

**14c-14 (MINOR).** The Tra/Cap boundary is too early. The functions from 0x7E9EA381 to 0x7E9EA459 are entries of the same app_check function table (0x7EC1C368, 119 entries) as the named `app_check_*` functions before them. After them come app_check helpers and the Tra event classes (ids 2201–2206 and the evTraCmp_* block 12061–12080, whose ctors 13c-event-ids.tsv itself lists as "CapBuf_BufferManager (next class)"). The first Cap function is the CapBuf getInstance 0x7E9EB318. The end at 0x7EB7FC90 is correct.

**14c-18 (MINOR).** The row ends its range at 0x7EB93385, but it also includes the 0x7EB93386–0x7EB933AA setters and the helpers up to 0x7EB93422, and the Ctg row begins at 0x7EB93423. The range end should be 0x7EB93422. Also, of the five helpers after the setters, only 0x7EB933B0 is used by DevSor (from 0x7EB931F5). 0x7EB933FC, 0x7EB93408, 0x7EB9340D and 0x7EB93417 each have a single caller in the display-device code at 0x7EB8D969–0x7EB8DFF4. Call them "helpers used by the display device (0x7EB8Dxxx)", not "DevSor helpers".

**14c-99 (MINOR).** Every handler mapping in the row is confirmed except the role of 11805. The handler writes a trace record first, as the 11775 handler also does. But its function is a synchronous wait. It builds an on-stack waiter (vt 0x7EC1C1F4), arms it for the code at +28 with HLS_EVENT, blocks on its semaphore with the timeout at +40, removes it, and writes the result (−1 = no event) to *(+32). This matches its use in 14c-110: CapTak slot 72 (End) with argument 1 posts 11805 with timeout −1 to wait for the end-of-take event of the returned handle. Suggested text: "**11805** wait for an event code (timeout +40, result to *+32; also writes a trace record)". The `14c-event-ids-extra.tsv` row for 11805 ("EVFW trace/record request") has the same error.

**14c-133 (MINOR).** The range, getInstance, initializeBuffer→CapTak, dumps, TraceDump and conversions are confirmed. The trace-logger sentence needs three fixes. (1) Kind is a value compared with `cmp` against 1, 2, 4, 8, 16 and 32 (masks 0x1–0x20), and the gate is `0x602B287C & kind`. "Bit 1/2/4/8/16" reads as bit numbers. (2) Kind 0x20 is missing; it prints a trace record via 0x7E9ED3C2. (3) 0x7E9EC76D is the kind-3 allocator (`BM_F_%d` with 3) of the same per-kind family. It is the only one that appends to the +220/+224 list, so "in-use list append" is right, but it lies after the stated allocator range 0x7E9EB7BC–0x7E9EC5C0.

**14c-144 (MINOR).** The mechanism is confirmed: 45-entry ctor table, walker id 3 with size 180, 22 member-pointer initialisers, 21 non-null tables each with exactly one dispatcher, the null table 0x7ED9855F with no dispatcher, the 77-record example and its read→loop→write dispatcher, all bases and counts, and 0 callers for all methods. Two details are wrong. First, the IGui_Controler table (0x602BB094, 22 records) has 9 null {0,0} records, so only 13 are {−1, method}. That dispatcher looks up one record by id and tests it for null; it does not call all of them. Second, the A6 text "the vtable 0x7F033AC4 stored by 0x7EECC6C7" names an instruction inside the dtor 0x7EECC6C4. The vtable (one slot, 0x7EECC6C4) is stored by the ctor 0x7EECC6AB and by the dtor 0x7EECC6C4. A minor nit: methods are shared between initialisers (395 records, 350 distinct methods), so "the initialiser" should be "initialisers".
