# Coverage review, round 7, batch 4 (F061–F080)

**Method.** For each function I first wrote a prediction from the map only: the regions table in `docs/firmware-map.md`, `modules.tsv`, sections 01, 08, 13b, 13d, 14a, 15a and 16b/16d/16e (the 16x row for the address). Then I read the code with `tools/fwmap.py` and `tools/disasm.py`, and I read descriptors, vtables and data tables directly from block 0.

**Name sources** (only to name things, not as map evidence):
- the D1 Ss table `scratchpad/d1/gui-toolkit/ss/handlers.tsv` (SS, state and event names);
- the OlyApi name table `scratchpad/d4/app/apinames.pkl`. The API id was read from the constant inside each vtable slot target, not from name order;
- the CA code-name table 0x7EEEFFD0 (`{code, char*}`, read from the bytes).

**Scratch.** `/tmp/scratch/04b1caa0-6975-4677-98e3-f42129671871/scratchpad/coverage7/batch4/` holds:
- the `fwmap fn --dis` dumps (`0x*.txt`);
- `rd.py`, a raw block-0 reader;
- `ss.py`, which decodes the 17 Ss descriptors (0x7EFB8BCC) and finds handler/entry/exit slots;
- `api.py`, which reads an OlyApi vtable slot and the API id in its target.

**Labels.** "Verified" = read in the code or the bytes. "Inferred" = from names, strings, call position or layout.

## CONTRADICTED items, with proof

**F066, 15a region row `0x7EDD7A57-0x7EDDA607 region helpers called from SS_MENU_LV handlers (0x7EDA4–0x7EDA8, 146 calls) and page 523; I: live-guide / LV-menu support` (also 15a line 33).** The start of this range is page-422 class code, not LV-menu helpers:
1. F066 works on the page-422 object. Its caller 0x7EDB3131 loads a0 from 0x7EDD713B (`mov (0x602BD5E0),a0`; on NULL `new(400)` and ctor 0x7EDD716A, the page-422 ctor in 16b). F066 reads and writes byte +397 of that 400-B object.
2. Its two callers are 0x7EDB3131 (SS_MENU_MAIN state 7 ART_MENU, event 0x9AD0) and 0x7EDD784D (a page-422 method, which the 16b row places "in page class (pages 422) code"). Neither is an SS_MENU_LV handler.
3. The next function 0x7EDD7A90 is also page-422 code: it calls the page-422 draw 0x7EDD7301, and its caller 0x7EDB31E9 is the ART_MENU handler for 0x9A45.
4. The LV helpers start at 0x7EDD7C32, the live-guide controller getter (RAM 0x602BD5E4, 52 B), which the SS_MENU_LV handlers call through 0x7EDD7C9D.

So the page-422 code ends at 0x7EDD7C31, and the 15a page-class row span "0x7edd713b-0x7edd7a57" ends 0x1DB bytes too early. That row's own note "code to next class 0x7edda608" disagrees with its span.

**F076, 16e row `0x7EEA7AE6 … vtable slot 18 (+72) of AVPI class vt 0x7F0307E8 (AFile Sink Plug-in group, by position)`.** The slot is right. The group is wrong, and 13b already has it right:
1. The only code that stores 0x7F0307E8 is the ctor 0x7EEA4D6C (`mov 0x7F0307E8,d0; mov d0,(a0)` at 0x7EEA4D84).
2. The only caller of 0x7EEA4D6C is 0x7EEA3028 (`AVPI malloc(1000)`). The only caller of 0x7EEA3028 is 0x7EEA7C7D, the Video Encode plug-in method at vtable word 0x7F0308AC. 16e itself labels that method "Video Encode Plug-in code".
3. The AFile Sink vtables are 0x7F0300B4/0x7F0301B8 (13b registry, factory 0x7EEA2154). 0x7F0307E8 is only after the `AFile Sink Plug-in` string in rodata order.

The same false group label is on **36 rows for vt 0x7F0307E8 and 21 rows for vt 0x7F0302D4** in 16e-graphics-avpi-index.tsv. All of them are the H.264 engine object, which the Video Encode plug-in creates.

3. **16b rows for Ss handlers built from locals** (F064, F065: "returns (SS<<8)|state assembled from locals (constants written include 0)") do not resolve the destination, although it is a constant in the callee (0x0409 and 0x0104 here).
4. **16b row for F068 leaves out `EditTrimming::save`,** which is its main call. The row reads only callee side effects (DM, setGuide, ShowPanelEx).
5. **16e family edge "maths 0x7EE5AC2B–"** is too high: F071 (0x7EE5A857, a matrix conversion) and its caller 0x7EE5AA2D are maths, but they are labelled "type modules".
6. **Not in the map:** the GUI EV-step tables 0x7EFE9622– (F078), the ADJSLF spectral tables 0x7F0DED34–0x7F0E7EA7 (F080; 08 names only the `SpectraChart.CSV`/`ADJ_BPF_*` calibration), the AVPI timer-entry class 0x0B04 (F075) and the H.264 engine history rings (F076).

## Where the map is weakest

1. **AVPI internals (0x7EE90235–0x7EEC5F31).** 16e gives only call-graph context for framework classes (F074, F075). It labels plug-in groups by string position, and this gave 57 false "AFile Sink" rows for the H.264 engine object (F076). No AVPI framework class has a role (timer list, completion counter, listener broadcast).
2. **3D engine and C3D class code.** The 16e rows give a type or class block by position and the callees, but no roles. Small, readable functions get no role: clz (F072), the float→1.12 matrix conversion (F071), the type-3 buffer size (F070), the child recursion (F069) and the class-41 position setter (F073). A shape rule (constant 4096.0f, clz masks, set-if-changed setters) would name several of them.
3. **GUI page methods outside their class span.** 15a class spans end too early (page 422), so the methods after them fall into a wrong "LV helper" region (F066). The 16b row then says only "helper with 2 callers".
4. **Ss handler rows give the wiring but not the effect** (F062–F065). The effect is in a guard or action callee, such as a reconnect on error 5, an end-play call or a guide-level commit.
5. **Rodata past the code** in segment 2/3 (0x7EEE1020–0x7F021020) and in overlay B (past 0x7F0D257C) is labelled only "read-only data". The two NOT-CODE items are structured tables (EV steps, spectral data) that the map does not list.
