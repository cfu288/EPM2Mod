# Coverage review, round 9, batch 4 (F061–F080)

**Method.** For each function I first wrote a prediction from the map only. I used the regions table in `docs/firmware-map.md`, `modules.tsv`, sections 08, 13d, 14a, 15a, 16b, 16d and 16e, and the 16x row for the address. Then I read the code with `tools/fwmap.py` and `tools/disasm.py`, and I read the data tables (touch-area table, pmf table, internal-control table, jump tables, vtinit fills, .data function tables) directly from block 0. None of the 20 functions is inside a `modules.tsv` range. DB `suspect` = 0 for all 20.

**Scratch.** `/tmp/scratch/04b1caa0-6975-4677-98e3-f42129671871/scratchpad/coverage9/batch4/` holds:
- the `fwmap fn --dis` dumps (`0x*.txt`);
- `rd.py` (raw block-0 reader, from round 8);
- `imm.py` (scans block 0 for a 32-bit immediate or data word);
- `mod.py` (modules.tsv range test).

**Labels.** "Verified" = read in the code or the bytes. "Inferred" = from names, strings, call position or layout.

## Other map errors and tool notes found next to the batch

1. **14a §"Vtable slots 0–3" and the 16e rows 0x7EE75C9A/0x7EE758CD/0x7EE65794: "node-type classes add `accept(visitor)` 0x7EE75C9A → the walk 0x7EE758CD" is wrong.** 0x7EE75C9A is the node level's **write of the child lists** (a write step, slot +4):
   1. The block-0 scan finds no immediate or data word equal to 0x7EE75C9A (`imm.py`), so it is never a vtable slot.
   2. 8 of its 10 callers are slot +4 write chains (step 3 after 0x7EE75DE0 root write and 0x7EE74A54): F072 (class 41), 0x7EE718E8 (46), 0x7EE72C6C (57), 0x7EE7AFBB (2), 0x7EE7DABB (3), and 0x7EE658A3/0x7EE65B4E/0x7EE6616F (16e itself says "calls 0x7EE75DE0 … 0x7EE74A54 … 0x7EE75C9A").
   3. 0x7EE758CD calls `a1->vt[+8](a1, count)`. This is the stream "write u32" slot that the root write 0x7EE75CF6 uses for +40. For each child it calls 0x7EE75E6A, which writes the child's class id through the same slot and then calls 0x7EE75E96 = `child->class->slot +4` (`mov (8,a0),a2; mov (4,a2),a2; calls (a2)`), the child's own write. So the code is a recursive serialisation of the children, not a visitor. The "accept override" 0x7EE65794 (base 0x7EE75C9A && 0x7EE65768) is probably one more write step of the same kind (I).
2. **fwmap mis-split in overlay B (F080).** The case bodies after a `jmp (aN)` through a {key, handler} search table become a separate "function" at the first case that has a data-word pointer. 16d then gives the callees of the other 10 cases "helper called by 0x7F09BB85" (0x7F09BFD5, 0x7F09C018, 0x7F09C053, 0x7F09C085, 0x7F09C0B0, 0x7F09C0FD, 0x7F09C136, 0x7F09C192 …). They should be "case bRequest N of 0x7F09BB22". The `jmp (aN)`-plus-table test that round 8 asked for (16b merged methods) would also catch this.
3. **16b row F061: "DM get block ?" is block 0** (d0 = d2 after `clr d2` at 0x7ED4FD2D). The argument tracker does not follow a register that was cleared earlier and reused.
4. **Not in the map:**

## Where the map is weakest

1. **3D engine type modules (0x7EE294B5–0x7EE5B5BB).** All 5 P rows in the batch (F067–F071) are context only. The roles are short and easy to read: an MCM field reader (F067), a vec3 keyframe evaluator (F068), a two-array object create (F069), a state snapshot (F070), a per-element flag set (F071). There is no name for the engine types (14a open question 2) or for the .data function tables. A rule could name the .data tables by their entries' common shape (track evaluators, interpolators).
2. **C3D helpers outside the vtinit slots.** The S rows are right (F072, F076). The tree walks and lookups F073, F074, F075 get only "shared helper". These are recognisable shapes (child/sibling/parent walk with a class-id filter; a jump table on the class id). The slot names have an error too: the node level's write was taken for `accept(visitor)` (item 1).
3. **USB device core in overlay B.** The map knows the MMIO, the ISR and the "EP0 state machine", but not the standard-request table. A mis-split hides the GET_DESCRIPTOR case (F080). F079's bulk phase is context only.
4. **GUI helper code that is not a table entry.** The rows give callee effects (setText, getSetting ids) but not the purpose (F062, F066). The GUI setting ids (91, 133, 4) and the DM block layouts (41, 71) are named only in single sibling rows, not in a dictionary.
5. **AVPI support code.** The pool layout F077 gets only "helper of the AVPI heap". This is the same gap as in round 8 (framework classes and plug-in slots without roles).
