## CONTRADICTED items with proof

1. **F053 0x7ECE0E3C (and its pointer entry 0x7ECE0E37): "→ same state" is false.**
   - The Pc descriptor 0x7EEDADE8 is {0x600A, rows 0x7EEDAD00, 4}. All four rows (0x04000011–0x04000014) are {event, 1, 1, 0x7ECE0E37}.
   - The row runner 0x7ECDF538 does `mov (8,a1),d1; mov d1,(92,a0)` (row.next → ctx +92), then `mov (40,sp),a1; calls (a2)`, so the handler gets the same ctx in a1.
   - The handler does `mov a1,a2 … mov 24576,d0; mov d0,(92,a2)`, so next = 0x6000. 0x6000 is the first Pc state (descriptor 0x7EEDAD70 {0x6000, 0x7EEDA4D0, 6}).
   - It also posts SUB_EVENT_CHECK_USB_SELECT_SETTING (0x0900000F at +76).
   - The body row 0x7ECE0E3C lists only 2 of the 4 events. The pointer-entry row 0x7ECE0E37 lists all 4, also with "→ same state".
2. **F054 0x7ECE10CB: "→ same state" is false.** It is the same mechanism: the row in descriptor {0x6004, 0x7EEDA740, 8} has next = 1, and the handler sets +92 = 0x6000, +28 = GUI code 133, and +76 = SUB_EVENT_START_FIRMUP.
3. **How common this is (V scan, approximate):** 16b has 545 CA-range rows that say "→ same state". The handlers of **56** of them contain a store to `(92,aN)`. So their next state may differ from the row's static value. 16b reads the row's `next` field and never looks at what the handler writes to +92.

## Weakest areas

- **CA_MAIN next-state semantics (16b).** The "→ same state" label comes from the static row field. It ignores handler writes to ctx +92 (about 10 % of the "same state" rows). The SUB_EVENT_* requests a handler sets at +76 are not reported at all, and the map does not cover the PC device-link firmware-update request (CBK_DEVLINK_REQ_FIRMUP → SUB_EVENT_START_FIRMUP).
- **Drawing engine and resource helpers (16b, 14e).** F055 and F056 have context-only rows.
  - The map does not cover the pen-tip modes at DC +46, the ellipse routine 0x7ECFBF17 or the style table 0x602B60D4.
  - 14e calls DC +40/+42 "scale", but F055 uses them as the dot size.
- **Unnamed objects and panels.** The map names the shapes but not what they are for:
  - the Com_ singleton 0x602B48F0, which wraps Cab_CameraBase;
  - panel 22, whose screen is unknown;
  - registry id 3, which looks like the panel-100 warning viewer.
- **Function boundaries.** The DB merges vtable-only stubs into the function before them (F051 holds slot 50 of the Ctg_ComponentSwitcher vtable). Those stubs then get no index row.
- The app-layer statechart code (16a, 13c, 15c) is the strongest part of the map. All the state numbers and roles checked in this batch are right.
