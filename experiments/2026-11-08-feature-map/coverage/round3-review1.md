## CONTRADICTED items, with proof

1. **F011 0x7E64015E is in the imgdev driver, not cam_lens.c** (contradicts 14b §1 "cam_lens.c ~0x7E63E5xx–0x7E640857").
   - Its callee 0x7E63EB3F returns 0x8481, which belongs to the imgdev error family. cam_imgdev.c uses 0x8480/0x8481/0x8485/0x8486 (0x7E63C169…). cam_lens.c uses only 0x9211/0x9213/0x9280, and all of them are at 0x7E640271 or later.
   - The 32-bit damage codes agree. The last 0x0A17xxxx (imgdev, 14b §2) is at 0x7E63E658, and the first 0x0A25xxxx (CAMLNS) is at 0x7E640307.
   - Its RAM state 0x605552E4/0x605552FC is next to `g_imgdev_driver` 0x605552E0. Its callers are the cam_imgdev.c paths. Its descriptor tables 0x7E7B03A8–0x7E7B04CC come before the `CAMLNS` string 0x7E7B0500 in rodata.
   - Fix: imgdev (driver part) ≈ 0x7E63D0DE–0x7E6401FF; cam_lens.c starts at ≈ 0x7E640200. Section 03's own row ("CAMLNS 0x7E640200, start not fixed") is consistent with this; only 14b is wrong.
2. **F015 0x7E668353 and F016 0x7E66B36A are not SDET code** (contradicts 03 §7b "0x7E667400–0x7E675000 … the detection algorithm library" under SDET, and 14b's "SDET algorithm block 0x7E66C9A8/0x7E66DA1D").
   - Reachability over calls.tsv: callers inside SDET (0x7E662000–0x7E666EB8) reach only 2 functions in 0x7E666EB9–0x7E675000 (both via 0x7E673F91). Callers outside reach 122, mostly TAKE AF (0x7E592A4B, 0x7E592E39, 0x7E59A88D, 0x7E59AA32, 0x7E59B98A, 0x7E59BBD0, 0x7E59BCD9) and FCS_MOVIE (0x7E5E8044 with the string `mdet`, 0x7E5E85A0).
   - F015 and F016 are reachable only from TAKE.
   - The `mdet` shell (0x7E666EB9) and the EMS result-field dump (`block_trust`, 0x7E666FE8) are at the start of the block. The block is mainly the **mdet motion-detection / AF-tracking library** (name from the shell; tracking role I).
   - The resource loader 0x7E674F44 is also inside the stated range (F017), so the range end is wrong as well.

## Smaller map errors found along the way (not separate verdicts)

- **BC range start** (02 table): BC code begins at or before 0x7E53AEC5 (F005 chain), not at 0x7E53BAAD.
- **Lens firmware-update steps** (02 §1.9): there are more than 4 steps. Cmd 5 is a read-back check that loops back to cmd 4 on a mismatch, and cmd 6 (0x1006) and cmd 1 (0x1001) follow it. The error codes also include 0x6606 and 0x6609.
- **exp module end:** the regions table puts 0x7E6A1020+ under "Movie", and section 03 ends EXP_MOVIE near 0x7E6A0000. Code shows exp runs to ≈ 0x7E6A9400, as section 12 says (F020).
- **SYSFMEM modes:** the help-text mode numbers are hexadecimal (`STL_Read` = 0x400; F001).
- **Unmapped gap 0x7E45B67F–0x7E45CE11** (between `per_adc` and ADCONV): 0x7E45BB10, an asynchronous request/start with a callback at +32 (21 callers incl. the I²C health check), is used by the ADC-key code (F002).

## Weakest areas

1. **The 0x7E666EB9–0x7E675000 block** (F015, F016, F017). The map files it under SDET as "detection algorithm", but it is mainly the mdet AF-tracking library, plus the resource loader. Nothing in it is described at the function level.
2. **Camera-core module boundaries without strings.** The imgdev/cam_lens boundary is wrong (F011).
