## CONTRADICTED

**F069 0x7EE619C7, zlib/C3D-API boundary (08 §5).** The map gives zlib as "0x7EE5F5F3–0x7EE61F" and the C3D-facing API as "0x7EE61C–0x7EE63". These ranges overlap, and 0x7EE619C7 is only inside the zlib range. Proof that it is not zlib:
- zlib ends at `zmemcpy` 0x7EE619AC–0x7EE619BE, whose callers are inflate 0x7EE5FE61 and 0x7EE5FD73. The stubs 0x7EE619BF/0x7EE619C4 follow.
- No zlib or libpng function calls anything from 0x7EE619C7 on.
- F069's only caller chain ends in overlay code: 0x7EE61A59 → 0x7EE61A4F → 0x7F0A13F9 → 0x7F09DFD4.
- F069 allocates through a C++ vtable on its context and runs the C3D class registry 0x7EE64322. zlib allocates through `strm->zalloc`, which is not a vtable call.

Fix: zlib is 0x7EE5F5F3–0x7EE619C6, and the C3D API starts at 0x7EE619C7. This is a small error, but the map states the range as fact.

**Also found outside the batch (from F067):** the **DMP GL library does not end at 0x7EE21020**.
- The `{char *name, fn}` entry table at 0x7F023C74–0x7F024284 (194 `gl*` entries) has 91 entries at or above 0x7EE21020, from glTexSubImage2D 0x7EE21657 to glPointSize 0x7EE29468. Examples: the matrix stack (glPushMatrix 0x7EE25FD4), buffer objects (glBindBuffer 0x7EE27D5A) and vertex arrays (glVertexPointer 0x7EE28A76).
- The call closure of all 194 entries stays inside 0x7EE02000–0x7EE2946D.
- A different module starts at 0x7EE294B5: `MCA_`/`MCT_`/`MCE_` tags and the string `$Revision: #88 $` at 0x7EE295EE. C3D-side code (0x7EE6C7A7, 0x7EE6C9C6, 0x7EE7ADF9) calls it.

So the regions table ("0x7EE21020–0x7EEE1020: C3D engine …"), 08 §5 ("0x7EE21020–0x7EE5B C3D engine") and 13d §1 (GL = "0x7EE02095–0x7EE21020"; "its only callers are C3D (0x7EE2–0x7EE3)") are wrong for 0x7EE21020–~0x7EE294B4. That span is GL. At least some of the "C3D callers in 0x7EE2" are GL functions calling each other. 0x7EE21020 is the round 0xA00000 offset of the old regions table, not a real module boundary.

## Weakest areas

1. **The C3D object system, 0x7EE619C7–0x7EE8F4F3 (7 of 20 functions: F069–F074, plus F068 nearby).** The map has only "C3D-side code" and "C3D-facing API". The code is a structured C-with-classes framework that the map does not describe:
   - a 2.6 KB class registry 0x7EE64322 with about 55 registrations, each `{fn, ctor, fn}` plus two sizes;
   - the object header 0x7EE8F081 (59 ctor callers), root init 0x7EE75D3C, an intermediate base F073 (26 subclasses), and init chains that return a bool at each level;
   - a visitor walk 0x7EE758CD and an error setter 0x7EE62AD7 (259 callers);
   - angle math in turns (0x7EE5ACA6/0x7EE5ADA3).

   One pass over the registry would name the class tree.
2. **Library boundaries in 0x7EE02095–0x7EE63000.** GL runs to ~0x7EE294B4 (not 0x7EE21020). An unnamed `MCA_/MCT_/MCE_` module follows it. zlib ends at 0x7EE619C6. The GL `{name, fn}` table at 0x7F023C74 would name 194 functions for almost no work, but the map lists only the name strings.
3. **GUI function roles.** The areas are right, but these are not mapped: the BT callback→event table 0x7EFE2EF0 (22 groups, matchers 0x7EFE2FF8), the state **entry/exit** functions of most Ss states (F062 is the HIDE_MODE entry, which the map omits although it documents the state), the Rec_View_Viewer exposure display (F061), and the RAW-edit menu page (vtable 0x7F0032B8, F065).
4. **AVPI class internals.** The plug-in vtable groups are mapped (and they placed F075–F078 correctly), but slot roles are not: ready predicates, Clone/copy-ctors, member arrays.
5. **Overlay task internals.** TPC_DATA (F079) and SPC (F080) are named, and their string-labelled handlers are easy to place. Their state machines (TPC_DATA_STATUS_*, the SPC 7 s / 300 s timers, the APE event 0x041A0001 parameters 0x200/0x210) are not in the map.
