## Side findings

1. **modules.tsv mov_img.c / mov_kdg.c rows are wrong (V).** Row 49 puts `mov_img.c` at 0x7E6DAF9A (first = last fn, placement `string-order`, 0 naming functions). 0x7E6DAF9A logs `[MOV_KDG] mov_kdg_init() in/out`. The `mov_kdg_*` functions run from 0x7E6DAF9A (init, ready 0x7E6DB034, start 0x7E6DB0AC, end, stop, F023, check_disable, memory_getadrs, exec 0x7E6DB6D1, get_info …). Row 50 starts `mov_kdg.c` only at 0x7E6DBC3C. Section 04 §3.2 already has the right range, 0x7E6DAF9A–0x7E6DCB0D, so the map contradicts itself. The rodata name `mov_img.c` (0x7E806F06) is just before `[MOV_KDG] mov_kdg_init() in` (0x7E806F28). So mov_img.c's code probably ends just before 0x7E6DAF9A (I).
2. **modules.tsv extents stop at the last function that names the file.** Named helpers after it get no file: F027 `art_stl2ycc_buffer_check` and `art_stl2ycc2_pass3`/`pass_err` (0x7E72CAB9/0x7E72CB37) come after art_stl2ycc.c's last_fn 0x7E72C85B. F030 and the other `play_load_mjpeg_*` / `play_load_load_*` functions (0x7E9461B1–0x7E9468AE) come after play_load.c's last_fn 0x7E946041 (V).
3. **16d's module label "BT UART/patch tail" (0x7E913690–0x7E913956, 13 rows) is right only for its first part.** 0x7E91369B/0x7E9136E5 are the `bt_sio`/UART path (13f). But 0x7E913754–0x7E9137F8 are `[BT]SALLOC` allocators, and 0x7E913835 (`weird numeric value`), 0x7E9138A1 and F028 are pairing/security glue used by the SEC event handler 0x7E913F1E. That glue belongs with "BTAPI glue" (05/15d start that row at 0x7E913984). No section explains this label (V).
4. **The 16a own-string rule misses the `[tag]func_name field` log format again** (as in round 7 F037). F039 logs `[chls]app_playinfo_control_move_target target_no`, but its row is a call list. The sibling 0x7EA29ACA (`…move_relevant`) is probably the same (I).
5. **F024: a fatal AV-library error hangs the camera on purpose.** For `A_ERR_SEVERE` (0x80000004) the movie-playback AVSCA callback disables interrupts and loops forever at 0x7E6E11A0 (V). No section mentions this. 13b says Init returns 0x80000004 for "no memory". Both readings can be true (severe = out of memory), but the callback's name is SEVERE.
6. **F025's net behaviour** (V): it sets the step-buffer index to 1 if it was 2, else to 0. Its twin is a true 3-slot decrement. This could be a firmware bug or an intended 2-buffer toggle. It is not resolved.
