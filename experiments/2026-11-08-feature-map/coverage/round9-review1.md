## CONTRADICTED items

No function's main role is contradicted. Two details are false:

1. **EMS2 vs EMS1 in the mdet moving-object path (F019, and the 15b/16d row of 0x7E666C5B).** 16d calls F019 an "EMS2 frame" unit, and 15b/16d call 0x7E666C5B the "mdet EMS2 frame set-up" (the regions table: "first function 0x7E666C5B calls EMS2 0x7E4600B0"). The code shows otherwise:
   - F019 calls 0x7E460084(1) and 0x7E460030(1). Both go through the field reader 0x7E45FF3C, whose jump table 0x7E4C5634 maps fields 16–23 to `mov (0x99E00200…0x99E0020C)` and `mov (0x99E00180…0x99E0018C)`. 13f's MMIO table says 0x99E00000 = **EMS1** (IRQ 98, ISR 0x7E45FB1F).
   - 0x7E666C5B → 0x7E666E92 → 0x7E460030(1) also reads EMS1 ch1. Its other EMS callee, 0x7E4600B0, is `add 32,a0; retf`. It sits in the EMS1 part of the driver (before the EMS2 IRQ attach 0x7E4600CA) and touches no register.
   - The real EMS2 users (0x7E46012D, 0x7E460810 and the result decoders 0x7E460DB8/0x7E460FC2) are called only by the `mdet_ems2` job layer 0x7E670647–0x7E673D52 and by tracking. They are not called by the moving-object unit.
   So the moving-object unit reads EMS1 results (EMS1 is driven by TAKE 0x7E59E203/0x7E59E217 per 16c). The "EMS2" labels on it and on 0x7E666C5B are wrong as stated. The row is hedged (I).
2. **15d kernel row typo:** 15d says "per-CPU block (0x8FE00004)[(0x8050)] +28". Every kernel function read here (sns_ctx 0x7E436577, F002, del_dtq 0x7E437EF4) loads `mov -1880096764,a0` = **0x8FF00004**. The 16c rows say 0x8FF00004 correctly.

- **Context only (10):** F002, F003, F006, F007, F008, F009, F011, F014, F016, F017. These rows hold call-graph, string, service-call or exact-summary facts, and all are accurate as facts. ## Weakest areas

1. **EMS1/EMS2 helpers and their mdet users:** the field reader 0x7E45FF3C (24 fields, table 0x7E4C5634), the channel tests 0x7E460030/0x7E460084 and the buffer-size helpers 0x7E4613A5/BF are "shared helper" rows. Because they have no role, the map wrongly labels the moving-object path EMS2 (F003, F019).
2. **BC debug logging:** the `BC_DATA\MMDDhhmm.TXT` card log gated by prm 0x20A4 mask 4 (F007, and its sibling 0x7E53C9AE) is not in the map. 08 mentions only the X_COUNT/Y_COUNT strings.
3. **IMG block builder A sub-builders (0x7E54880E–0x7E54CD97):** 13a gives only the flag masks. No sub-builder has a role. F009 (flag 0x40) is the resize/scaler step and crop set-up, with the 16 MP sensor sizes 4608×3456 as divisors.
4. **Kernel memory management:** the kernel heap alloc 0x7E4365A8 and free 0x7E4366C6 (F002) are "shared helper" rows. 15d lists object create/delete but not the heap.
5. **Strobe code reached from ADJ (overlay B):** F014's mode switch (1–10 → 14/15/18 or RC-level selection) has no role in the map, although its only entry is the factory-adjustment task.
6. **Lens start-up and key 0x121C (F006):** the map names the key callback (0x7E53239A) as a "LENS_FOCUS_LIMIT handler step", but nowhere says what key 0x121C is or that 0x604F9502 mirrors it.
7. **cam_sg register writers (F017):** the 0x99900000 unit is still unnamed (13f "identity open"), so the command-7 apply step (0x999000B0/B4/B8) has no role.
