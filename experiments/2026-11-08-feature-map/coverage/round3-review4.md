## CONTRADICTED

**F064 0x7EDDDF93: the "self-adjust UI 0x7EDD8–0x7EDDF" label in 13d §1 is wrong for most of that range.**
- The `[GUI-SelfAdjust]` / `userGuiSelfAdjust::` strings are used only by 0x7EDDBF31–0x7EDDD1E5.
- Before them, 0x7EDDAF6A–0x7EDDAFFF are the `InitFocalLength / IncreaseFocalLength / DecreaseFocalLength` page (focal-length entry, inferred for the stabiliser), and 0x7EDDBD50 is the language-resource loader (`getLanguageLoadResource`).
- After them, 0x7EDDD22C–0x7EDDEB21 are GuiTouch action handlers:
  - The touch-action table 0x7EFED8F4 points at 0x7EDDDE22…0x7EDDE967.
  - All 35 callers of `checkSlideAreaPos` 0x7EDE13B4 (`[GuiTouch] checkSlideAreaPos Failed.`) lie in 0x7EDDD22C–0x7EDE033E.
  - F064 posts EVT_LVBAR_CHG_VALUE (0x9ACB, live-view bar), not a self-adjust event.
- The GuiTouch code runs from ~0x7EDDD21D to ~0x7EDE160x (the last helpers 0x7EDE15A3–0x7EDE15EE; `userGuiUsbConnectCallBack` 0x7EDE1D0A follows). So the 13d row "~0x7EDE0000–0x7EE01FF5 = menu pages" also starts in GuiTouch code. 13d §1 has no GuiTouch row. 07 cites only two GuiTouch functions (0x7EDE040E, 0x7EDE0983).

## Other map defects found (not verdicts)

- **08 §1.1 still gives "a DPS XML library at 0x7F061020–0x7F068F9C".** 13b and the regions table end DPS at 0x7F0645C0 and put the red-eye library at 0x7F0645C1–0x7F0691C5. So the 08 range covers F077 (red-eye) and is stale. The 08 row has no correction mark.
- **Overlay A code calls overlay B.** DPS code in overlay A (0x7F05C000–0x7F06B000) calls the overlay-B helpers 0x7F0879CD (malloc, 36 callers), 0x7F087BE5 (memset wrapper), 0x7F087BD1 (strlen wrapper) and 0x7F087BF9. 13b §1 notes the string helpers. Section 01's overlay table loads A (Usr2 bit 0) and B (bit 1) independently, but DPS cannot run unless B is also loaded (inferred consequence; the load order was not traced). The regions-table row "0x7F06B000–0x7F0AB000" also does not match 01's overlay-B copy range 0x7F080000–0x7F0EB800.
- **14a §2.1's internal-block label "shader/uniform back end 0x7EE10B33–0x7EE19609"** does not fit F069 (a general GL state-block creator whose sub-initialisers reach the texture and buffer areas). The label is marked inferred.
- **08 says C3D runs on CPU1, reached through the bridge tasks.** tasks.tsv puts the C3D task (0x0071), C3D_UPDATE and C3D_EXE_BRIDGE on CPU0 and only C3D_EXE (0x1002, 0x7F09DFD4) and two bridges on CPU1. F080 shows the CPU0 C3D task replying into the CPU0P→CPU1 bridge queue. The map should say which side renders. (Not decided here.)

## Weakest areas

1. **GUI app code between the named classes (0x7EDB–0x7EE0).** 8 of the 8 GUI functions were only PARTLY explained or wrong. The map names the ranges (Ss handlers, BT wizard, menu pages, userMenu*). But it has no per-page index: the Firmware-version page and its Movie flag (F061), the viewer behind registry ids 8/9 (F062), the Edit › Aspect page (F067), the text-entry page for ids 472/473/506/508 (F066), the P2S/S2P album transfer (F065) and Rec2_CompScale (F068) are not mentioned. A table of page id → singleton/vtable from the page-open functor 0x7EDCBE97 (ids 1..651, hash table 0x7EFE1914) and the registry 0x7EFE190C would cover most of these.
2. **GuiTouch is missing from 13d §1** (see CONTRADICTED). The touch-action tables (0x7EFED8F4 and its neighbours) and the LVBAR events are not mapped.
3. **AVPI framework and plug-in internals.** 13b §2.4 says "individual class roles are not mapped". F072 (graph start barrier), F073 (callback adapter) and F074 (struct-driven MP4 box writer) confirm that this region is mapped by layer only.
4. **Overlay-B C3D bridge and scene code.** 14a lists the tasks and the scene object names. The display/geometry set-up (F078), the shared image buffer (F079) and the C3D reply path (F080) are not described, and neither is the CPU0/CPU1 split.
