## CONTRADICTED items

1. **F021 0x7E8FF8A0 is not `iap_cmd_prc` (16d).** The string ` iap_cmd_prc error:` is printed after `call 0x7E91C673` at 0x7E8FF914, using that call's result. So `iap_cmd_prc` is **0x7E91C673**, the dispatcher on ctx byte +906. 16d calls 0x7E91C673 only "the iAP dispatcher". F021's own first string is `link_callback() flg =`, and F021 is the callback passed to `cp_init` (0x7E9007EE) (V). The "own string (io)" rule took a callee's error message as the function's name.

2. **The `sdk api` table is at 0x7EBF8180, its layout is `{cmd*, name*, handler*}` and it has 636 entries, so every one of the 631 `sdk-api` rows in 16a has the wrong command (F030, F032; also F031's caller name).** 06 §5 says "635-entry table at 0x7EBF8188 … `{handler, "A02", "shutDown"}`". The proof:
   - The dispatcher 0x7E9A074B loads **0x7EBF8180** (`mov 2126479744,a2` at 0x7E9A07E6 and 0x7E9A0823). It compares the input with the string at (a2), calls **(8,a2)** (`mov (8,a2),a1; calls (a1)` at 0x7E9A0839), steps by 12 and stops at **636** (`cmp 636,d2`) (V).
   - So entry 0 is {"A01", "initializeApi", 0x7E9A171D}. 16a calls 0x7E9A171D "A02 shutDown".
   - **String proof:** 0x7E9BF9E5 contains `OlyShell_FlashAir__connect`, but 16a calls it "sdk api handler t10 disconnect". 0x7E9BFA44 contains `OlyShell_FlashAir__disconnect`; 16a calls it "OlyApi FlashAir::disconnect" with "vt word 0x7EBF9F4C", but that word is the handler field of the last table entry (t10).
   - **Whole-table check** (`sdkchk2.py`): I took the first OlyApi id that each handler passes to the name lookup 0x7E96E5F0 and compared that method name with the entry name. With the layout above, **560 of 566** match. The other 6 are spelling variants (getHlsStateS004243 / getHlsState, eraseALL / eraseAll, moveCursor / MoveCursor, m01 start / startEasyPrintService, m09 end / endEasyPrintService, A41 setHlsStateS004243 / setHlsState). With 06's layout, **0 of 565** match (`sdkchk.py`) (V).
   - F030 calls vt+12 of `OlyApiEditShadowAdjust` (vptr 0x7EC0EC28 → 0x7E9C3ECA save) and prints id 0x030C08 (save). F032 calls vt+92 of `OlyApiBluetooth` (vptr 0x7EC0E920 → getPairingDeviceCount) and prints id 0x050418 and `count` (V).
   - **Fix:** in 16a, each `sdk-api` row should take the command/name of the entry **before** the one it shows now. 06 §5 should give base 0x7EBF8180, layout {cmd, name, handler} and 636 entries. "The word after the table (0x7EBF9F4C)" is in fact the last handler field.

3. *(not counted as a verdict)* **F028 has the wrong class in 16a** (verdict PARTLY, because modules.tsv names `OlyHfwOpeBGrCtl.cpp`). See side finding 1.

## Side findings (not counted)

1. **16a calls the whole OlyHfwOpeBGrCtl block "OlyHfwOpeShoot method".** Examples: 0x7E98A854 (`OlyHfwOpeBGrCtl::draw#`), 0x7E98ABD9 (`OlyHfwOpeBGrCtl::draw() UnResponsive`), 0x7E98B0E4 (`::getDrawState`), 0x7E98B1CD (`::preprocessDraw`), 0x7E98B2F7 (`::setImageAreas`), 0x7E98B5A9 (`::setMenuArea`) and F028. All of them carry `OlyHfwOpeBGrCtl::` strings, but their rows start "OlyHfwOpeShoot method" (V). 15c already says this range holds BGrCtl, but 16a takes the class from the range. 15c should give BGrCtl its own sub-range (about 0x7E98A854–0x7E98B7BD).
2. **The `HLS_CW` queue (id at 0x7E43EDFE) is not in the map.** 0x7E98B7BE passes `HLS_CW` to 0x7E4491E8, which is a stub that returns 0 (16c), so the queue is not created there. `api_exec_receive_msg` 0x7E67E8A9 handles queues 0x7E43EDFC and 0x7E43EDFE differently: it reads them directly, with no 0x7E67EB58 semaphore wait (V). 0x7E98CD47 and F029 use this queue (see F029).
3. **0x7E961ABB hash keys are cmd − 1.** The 16d row of 0x7E961ABB quotes key values as case numbers ("case 0x500 … case 80 … case 0x5000"). Those match the table words, but the code compares them with (cmd − 1). So the table word 0x4FF is command 0x500, the word 0x1FF is command 0x200 (also F026), and so on.
