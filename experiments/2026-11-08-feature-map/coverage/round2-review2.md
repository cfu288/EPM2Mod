## Contradictions

No sampled function's role is contradicted. Three map statements were found false while checking the batch:

1. **13c §6, soft (over-general claim).** 13c says "The update callbacks of these observers [base 0x7EB85D67] have the 75-byte observer-callback shape". F035 shows this is not always true. `CapBlu_BluetoothEv2Observer` has ctor 0x7EA5119D (`call 0x7EB85D67`, vtable 0x7EC412F4) and dtor 0x7EA511B2 (`call 0x7EB85D75`). Its slot-0 update 0x7EA511D1 is 35 bytes. It logs and calls notify-all 0x7EB86ED0 on this+24, and it creates no event. So some observers relay to a second observer list instead of turning the notification into an event.
2. **modules.tsv row `mov_art.c` (and a tool bug).** The row reads `7e6cbfd3 7e6cbfd3 mov_art.c 0 string-order 7e7fe50f`, which says no code names the file. The string is really at **0x7E7FE510**: bytes `38 e2 7f 7e` + `mov_art.c`, so a pointer word ending in 0x7E is directly before it. Six code sites load 0x7E7FE510: 0x7E6CBF49, 0x7E6CC733, 0x7E6CCEED, 0x7E6CCF37, 0x7E6CD4E2, 0x7E6CD6E3 (V). So the module is "direct" with 6 sites, and it starts at or before function 0x7E6CBEBC, not 0x7E6CBFD3. **Cause (tool):** the fwmap string scanner treats the 0x7E byte as `~` and starts the string one byte early. The code reference to the real address is then lost. `fwmap str '^~'` lists 201 such strings, and 137 of them have 8+ characters, e.g. `~art_IsSupportType in`, `~art_filter_09_diorama in`, `~mov_dsp`, `~--CapBlu_BluetoothEv2Observer::update`. All but one show `fn: -`, but code does load the +1 addresses: checked for 0x7E854884, 0x7E8570C0, 0x7EC412CC and 0x7E7FE510. strrefs.tsv therefore misses these references. The other string-order rows (mov_img.c, mov_rec_file.c) are not affected.
3. **Region table / tool (not counted as CONTRADICTED).** 0x7E7F0F78–0x7E7FABB4 is an embedded touch-controller firmware image (F023). The map has only "strings and tables" for this range, and section 08 names the bootloader but not where its payload is. build/map has 29 "functions" in the image and 103 in the OKAO model area (F024), all with `data_page = 0`. So the data-page heuristic does not catch high-entropy or binary tables in the 0x7E73–0x7E8E data region.

## Where the map is weakest

- **Embedded binary payloads in the 0x7E730000–0x7E8E0000 data region.** The touch-panel firmware image (≈40 KB, Cypress-style bootloader records, I) is unmapped. Spurious "call"-sourced function starts fill both this image and the OKAO model blob. A sweep for high-entropy or record-structured data with no pointer references would find more.
- **C++ Cap/Cmp class internals.** Most of this batch (11 of 20) is in the app layer. The map has the class *names* (13c §5) and the generic statechart shapes, but no per-class roles for BufferManager, MediaInfo, ThroughImageFacade, GpuSlideShow, RecViewController or ShootingComponentBase. One class, the `app_control_sound_*` voice-memo sound control at 0x7EA61958–0x7EA62192, is missing from the class directory.
- **Shape table gaps (13c §3).** It has no row for Rhapsody `initRelations` (F034), dtor-side container teardown (F033), guard/choice transitions after a timeout (F039), or relaying observers (F035).
- **Event payload semantics.** The 32-bit codes in event 11779 (0x0417000x, F036) and the receiver singleton 0x602B1FE8 / 0x7E974D11 (482 callers, `COMRCP` strings) are not described anywhere.
- **Settings without a feature.** Info 667 / prm 0x3111 ("MF setting", F029) is in 07-settings.tsv with hints, but no section says what the start/endMFsetting mode is.
- **String index.** The `~`-prefix bug (side finding 2) silently drops code references to strings that follow pointer tables. This affects art trace strings, module tags (mov_art.c) and class-name strings, so string-based module placement and "fn: -" (unreferenced) claims near pointer tables need re-checking.
