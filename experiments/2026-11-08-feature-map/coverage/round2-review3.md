## Map claims that the code contradicts

**C1. Dev* part 1 ends at "~0x7EB93A80" (13c §1, and the same row in the regions table through 13c).**
- **The map says:** 0x7EB8C265–~0x7EB93A80 holds `Dev*` device classes (display, DevAef, DevCls, effects, LED, DevMed, DevRec), and the `Ctg_ComponentSwitcher` categories start at ~0x7EB93A80.
- **The code shows:**
  - The last `Dev*` string user is `DevSor::stop()` 0x7EB93362.
  - From 0x7EB93423 there is category code with no device API calls:
    - the 852-byte function-mode category: getInstance 0x7EB93423 (its only caller is `Cab_CameraBase::functionModeState` 0x7EB8AA26), ctor 0x7EB9345E, vtable 0x7EC8F144, setActiveContext override F054;
    - its sub-category 0x7EB937D3/0x7EB9380E/0x7EB938CB, which gets `CmpFnc_FunctionComponent`.
  - So the Dev/Ctg boundary is about **0x7EB93386–0x7EB93423**, not 0x7EB93A80.
- The map also contradicts itself. 13c §5.3 calls 0x7EB938CB "the Ctg area", but by 13c §1 that address lies inside "Dev* part 1".

**C2. `CmpSts_MfAssist.cpp` 0x7EB7DEB9–0x7EB7E77A (06 §2 table).**
- The class starts well before 0x7EB7DEB9:
  - its ctor 0x7EB7D14B (13c §5);
  - F051 0x7EB7D7E8, `CmpSts_MfAssist::evTraReqShtEndMfAssist`.
- 0x7EB7DEB9 is only modules.tsv's first function that names the file. This is the same first_fn ≠ file-start problem as round 1 (F046/F050): in this batch it also affects CmpCPic (code to ~0x7EAB8895, map last_fn 0x7EAB5D98) and `Cmp_ComponentManager` (06: code 0x7EA7CB15–0x7EA7DBAC, but its ctor 0x7EA7C89C and its observers 0x7EA7E52A–0x7EA7E66A lie outside that range).

**Imprecise (not counted as contradictions):**
- 13c §3 says "CmpSts controllers use `Com_ManagersSubTransition` 0x7EB8573D (15)". Only 8 of the 15 callers are CmpSts. The others are the three CmpCst_* components, Cmp_OutlineController, Com_ActiveTransitionManagerBufferd and 2 unidentified callers (0x7EA6CF32, 0x7EA77CBA).

## Where the map is weakest (from this batch)

1. **Event semantics in the component protocol.** The shapes are recognised, but the ids that carry the protocol are unnamed:
   - 12063/12068/12069: ComponentManagerWithBoot observers → every component;
   - 26798: each component's reply to +484;
   - 11988: MfAssist answer id.
   - Each of 12063/12068/12069 is tested in 44 components, yet the TSV has no name, sender or handler for them.
2. **The shooting sequence's interface to TAKE.** The map does not mention:
   - the take-ready requests (`TAKERDY_NORMAL/FAST/ABORTPROC_send` through the take capability at +432);
   - the QUICK / QUICK_RELEASE take-picture sub-states (F042);
   - the shutter black-out handshake (`BLACK:ON/OFF`, the PaintBlack flag 0x602B0D20 in TraShareTakeStatus, the display-device `startPaintBlack`) (F043).
   - Section 13e covers TAKE_* from the task side only.
3. **The meaning of capability vtable slots.** Play/Edit state entries call +860 and +832 slots (vtbl+180, +308, +460, +508, +464, +448…) on every path. The map does not say which capability sits at +860 or +832 or what the slots do (F044, F046, F048, F049).
4. **GUI toolkit below the class level.**
   - Roles of widget 0x8005 (image button with normal/selected/disabled images, I) and of class 0x0104.
   - The meaning of status bits 16 and 0x10000.
   - Container child management (F055).
   - The pixel-format/surface layer in the drawing engine (F057).
   - 13d has the right ranges and the setter signature, but almost no per-method roles.
5. **Ctg area start and the function-mode category** (C1). The map's category list begins with the 5 Ctg_ComponentSwitcher vtables. It misses the function-mode category tree that `functionModeState` builds.
6. **GUI Live Bulb/Live Time path** (F060). The live-view element reads `Shooting::getLiveBulbInfo` through a member-function-pointer table that a 2.9 KB static initialiser (0x7ED98B95) fills. Neither is mapped.
   - **Tool note:** fwmap gives 0x7ED98B95 0 callers and 0 callees. Function-pointer tables built in RAM hide these targets from xref; only the raw `mov imm32` at 0x7ED99526 shows F060.
