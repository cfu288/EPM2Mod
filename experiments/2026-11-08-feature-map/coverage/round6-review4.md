# Coverage review, round 6, batch 4 (F061–F080)

**Method.** For each function I first wrote a prediction from the map only: the regions table in `docs/firmware-map.md`, `modules.tsv`, the sections (01, 07, 13b, 13d, 13f, 14a, 15a, 15d) and the 16a–16d index row for the address. Then I read the code with `tools/fwmap.py` and `tools/disasm.py`, and I read vtables, registries and data tables directly from block 0.

**Name sources.** I used these only to name things, not as map evidence:
- the D1 Ss handler table `scratchpad/d1/gui-toolkit/ss/handlers.tsv`, for SS, state and event names;
- the OlyApi name table `scratchpad/d4/app/apinames.pkl`, for API ids. The OlyApi vtable slot of a method was read from the id constant inside the slot target. It was not taken from name order (see "Other map errors", item 4).

**Scratch.** `/tmp/scratch/04b1caa0-6975-4677-98e3-f42129671871/scratchpad/coverage6/batch4/` holds:
- the per-function `fwmap fn --dis` dumps (`*.txt`) and copies with hex immediates (`*.txt.h`);
- `hx.py`, which converts decimal immediates to hex;
- `rd.py`, a raw block-0 reader;
- `mapgrep.py`, an address and range grep over the map, with its output in `mapgrep.txt`.

**Labels.** "Verified" = read in the code or the bytes. "Inferred" = from names, strings, call position or layout.

## CONTRADICTED items, with proof

**F070, 16b row `0x7EE01FF5 … case block (key 282) of hash switch {key, case} 0x7F01170C in 0x7EE01F66 (split off by fwmap) hsw V`.** This row is false on three points:
1. **It is a whole function, not a case block that fwmap split off.**
   - It has its own prologue, `movm [d2,d3,a2],(sp); add -16,sp` (0x7EE01FF5/0x7EE01FF7).
   - It has its own epilogue, `ret [d2,d3,a2],28` (0x7EE02092).
   - It is entered through `calls (a0)` at 0x7EE01F7F, after `mov (4,a0),a0`, which loads the row's function word.
   - The caller continues after the call: `mov d0,d3; cmp 0x7D0,d3; …`. A case block would not return to the code after the switch.
2. **The table is not a hash switch.** 0x7EE01F66 scans it linearly: `inc d2; add 8,a0; cmp 10,d2; lcs`.
3. **282 is only one of its keys.** The 10 rows are {0x11A, 0x14E, 0x14D, 0x14F, 0x14C, 0x152, 0x1CD, 0x1CC, 0x1CE, 0x1CB}, and every row points to 0x7EE01FF5. In 07-settings.tsv these ids are the info ids of tag 0x18A1 (282), the 4-element array tag 0x72A1 (332–335) and the 5-element array tag 0x3051 (338, 459–462).

The 14a note ("GUI code; reads info 109/279/44; 10 data words") is correct.

## Other map errors found next to the batch (neighbour rows; proof in the bytes)

1. **16b row 0x7ED16C72 and 16b md line 155: the table address "0x7EF04808" is wrong. It is 0x7EF03C08.**
   - The code is `add 2129673224,a2` = 0x7EF03C08, at 0x7ED16C7D.
   - 0x7EF04808 holds unrelated words (0, 0xFFFF0000, 0x00D10000…).
   - The table is `{u32 panel type, fn}`, indexed by d0 = panel index. Its function is called with d0 = the display-variant byte at RAM 0x602B61F4. The 16b text "#d0" is right in shape, but the address is wrong.
2. **16d row 0x7F09E9EE names this function `` `glSetErrorFuncDMP` ``. That is wrong.**
   - 0x7F09E9EE is the overlay C3D scene start function. It *calls* `glSetErrorFuncDMP` 0x7EE097F9, and 14a line 80 says this.
   - It also calls EGL up 0x7EE61E35 and the scene init 0x7F0A13F9.
   - The wrong name spreads into the "under `glSetErrorFuncDMP`" context of other 16d rows (F078, 0x7F09FA1A, 0x7F09FBA8).
3. **16d row for F076: the BASIC table is misread.**
   - The table starts at 0x7F069338, not 0x7F069340.
   - Its rows are `{name, token, fn}`, not `{fn, name, id}`.
   - Proof: see the F076 evidence. Under the 16d reading, `?` would share a handler with `for`, and `goto` with `rem`.
4. **The method rule in the round-5 review-4 header is not general.** That rule is "OlyApi slot vt+N is the (N/4+1)-th name". For CustomPrint, vt+60 loads 0x05031D `canPrint` (the 29th name) and vt+84 loads 0x050320 `getPrintCount` (the 32nd name). Read the API id in the slot target instead.
5. **13b, "12 plug-ins" 0x7EE9C332–~0x7EEC1B71, is not plug-in-only.** The shared sample-pool class (vt 0x7F03002C, F074) sits in this range and is used by three plug-ins. 13b SCA can now say that message 0x103 = Run = session vt+12 (verified; the map has "inferred"). It can also say that the task-side Init accepts only session types 6 and 7.

## Where the map is weakest

1. **No function index for 0x7EE02095–0x7EECE318** (DMP GL, 3D engine, libpng/zlib, C3D framework, AVPI). The 16a–16d scopes leave this range out, and 5 of 20 batch functions (25 %) fell in it. The C3D part can be classified from the 14a byte signatures and the class tree (F072). The AVPI framework classes, plug-in internals and SCA session classes have no roles at all (F073–F075).
2. **16d overlay-B rows are almost all "gist" context.** They list strings, MMIO and nearest named ancestors, and the components are labelled "(I, position)". The USB device ISR chain (F077), the ADJSLF helpers (F079, F080) and the C3D scene code (F078) get no role, although 01 and 13f hold enough to name them.
3. **16b "private method" and "helper of X" rows for panel and page code** (F061, F066, F067, F068) are context only. The panel-type layout table 0x7EF03C08 and the GUI trace ring buffer are not described anywhere.
4. **The 16b hash-switch (`hsw`) rule** produced a confident V-labelled row that is false (F070). Rows with this basis should be checked for a real prologue and `calls` entry before they are trusted.
5. **Ss handler rows give the state wiring but often not the effect.** For example, F063 "go to MOVIE_VOL" does not say that it lowers the volume, and the `does:` field is empty when the effect sits in a callee.
