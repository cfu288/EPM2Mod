# Coverage review, round 6, batch 1 (20 functions)

Target: E-PM2 v1.6 block 0, database build/map (current). For each function I first wrote the map's prediction from docs/firmware-map.md (regions table), modules.tsv and the sections (01–16d, with the 15x/16x TSV indexes). Then I read the code with `fwmap.py fn/xref/range`, `disasm.py` and the ROM bytes. **V** = read in the code or bytes. **I** = inferred. One function (F019) has `suspect` = 1. The other 19 decode as normal code.

modules.tsv places only 4 of the 20 functions in a file: F013 and F014 in cam.c, F015 in cam_still_live_bulb.c, F018 in mcon. The other 16 predictions come from the regions table, the sections and the 16x rows.

## CONTRADICTED items

**F015 0x7E660D79: "live bulb step callback" (15b-camera-core-index.tsv line 1885, copied to 16d-core-play-overlay-index.tsv line 2935, class S).** Proof:
- It has a direct caller: `call 0x7E660D79` at 0x7E660BE5 in 0x7E660BB9 (xref V). It is not loaded as a pointer anywhere.
- Its body is one named-pool take: `mov 0x7E7BF6F6 ('S_LB_M'),a0; mov 40,d0; mov 6,d1; call 0x7E642097`. A loop stores the 6 returned pointers at 0x6056EDAC + 4·i and zeroes 40 bytes each. There is no event, no state and no step logic.
- The chain is 0x7E65DB3D (LB init) → 0x7E660BB9 → 8 allocators. This is init-time allocation, not a per-step callback.
- The same mislabel covers the whole family, because the cbx.py rule turned "immediates before the call" into "callback". I checked 0x7E660C21, 0x7E660E7B (LB, both `S_LB_M` pool takes with the single caller 0x7E660BB9) and the still sibling 0x7E65C6A1 (`STILL` pool take, single caller 0x7E65C639) (V). So the 86-byte rows 0x7E660C21–0x7E660E7B and the 86-byte "still step callback" rows 0x7E65C6A1–0x7E65C8FB are probably all wrong the same way (I for the ones I did not open). The prose in 15b (line 126, "86-B request builders … named pool take 0x7E642097") is nearer the truth than its own TSV, so the map contradicts itself.

**Smaller errors (not counted as CONTRADICTED):**
- 16d calls 0x7E611515 `FCS_END` in the "under …" context of 22 rows. `FCS_END` is a trace string inside it. The function is the FCS_MOVIE 0x1600 / `CONTSTILL` handler.
- 14b §1: "7 pointer-only methods 0x7E579AB7–0x7E579C17 of vtable 0x7E78EEBC". The vtable also has 3 base-class slots (0x7E5795F4, 0x7E5796E4, 0x7E5797CB), and slot 0 is F008 0x7E579B45.
- 13f/15b present the ADC request path as live. F003's channel 0x82 is not in the 9-entry channel table, so that start-up request never runs on this body.

## Where the map is weakest (this batch)
