Target: E-PM2 v1.6 block 0, database build/map (current). For each function I first wrote the map's prediction from docs/firmware-map.md (regions table), modules.tsv and the sections (01–16e, with the 15x/16x TSV indexes). ## CONTRADICTED items

**F006 0x7E52463F: 16c files it in the sub-group "lens module > `lens` debug shell (sub-commands, dumps)".** This label covers the range 0x7E523E85–0x7E52A41D (151 functions). Proof that F006 is not shell code:
- It is registered at start-up, not by a shell command. LENS_MAIN start-up 0x7E51C129 calls 0x7E524169 right after the lens state reset 0x7E51F893. That function stores F006 in the hook 0x604F9070 (`mov 0x7E52463F,a0; call 0x7E52257D`) with no condition.
- The hook is called in the normal lens flow: at the end of 0x7E520387 (`mov (0x604F9070),a0; calls (a0)` at 0x7E5204C4, ← LENS_MAIN handlers 0x7E51C7A4/0x7E51CBBD) and in 0x7E5204D3 (0x7E520A46).
- Its body is timing logic: the lens sync state 0x7E5373D7() = 2, the elapsed µs, a 2850/3500 µs guard, then hardware timer channel 7 or an immediate lens request submit through 0x7E5247D6 → 0x7E51F98E.
- Its only printing is the trace tags `t3`/`t3/` under debug masks.

The shell dispatcher (0x7E524C76, 02 §lens) starts after F006, so the sub-group's lower bound is too low. 0x7E524169 (the scheduler init) is also in that range and is not shell code either (I for the bound; V for these two functions).

## Other errors found (outside the verdicts)

1. **Pin-op dispatch layer filed as EMS (V).** 16c labels 0x7E4613E5 and the dispatchers 0x7E4613FD–0x7E4614F1 as "EMS1/EMS2 motion-estimation drivers". They are a 7-unit pin abstraction: pin = (unit << 24) \| n. There are ≥ 12 op tables of 7 pointers at 0x7E4C584C + 28·k. Users include 0x7E461433 (op 4, 17 callers), 0x7E46144E (op 5, 23 callers, also the `gio` shell) and 0x7E461469 (op 6, 61 callers). Unit 0 is GIO 0x9A100000. Unit 3 is F003's 0x98B007xx bank. 13f does not describe this layer.
2. **Wrong table sizes in 16c table-slot rows.** F003's "(3 entries)" and 0x7E4622E8's "table 0x7E4C58D8 (2 entries)" should both be 7. 0x7E461712 is called "slot 7 of 0x7E4C584C", but it is slot 0 of the next table, 0x7E4C5868.
3. **F003 extent.** The DB merged the unit-3 stubs 0x7E4622DC/DF/E2/E5 (ops 1–4, `retf`) into F003. Each stub is a separate table target.
4. **F004 row offset.** The row says "stored at +4"; the code stores F004 at +0.
5. **F019 row condition** ("when 556 or 480 changed"): 480 is never compared before and after (see the notes).

## Where the map is weakest

1. **Lens module internals (F005, F006).** 16c sub-groups are address ranges, and their names can be wrong (the "debug shell" range holds the timed-transmit scheduler). The map has no model of the lens sync/transmit timing (the 0x604F9070 hook, the 0x604F9188 sync, hardware timer ch 7, the `t3`/`t5`/`t6` trace tags), and no names for the channel-state variables (0x604F8F30 etc.).
2. **Low-level platform glue below the drivers (F002, F003).** The pin-unit dispatch and its 0x98B007xx bank are missing or misfiled. The ISRs are named only by IRQ number, not by what they serve (RTC alarm).
3. **Middle-layer helpers with a generic row (F008, F013, F015, F016, F020).** The module is right, but the row is a call-graph or strings summary. The roles (sub-command, state machine, movie corner codes 0x8002–0x800E, gesture trace, OKAO work block) have to come from the code. In AF, the VHPF hill-climb states 32/34/35/48/53/54/56/80/86 are not documented.
4. **MEC request plumbing (F004).** 14b names the command layer and the codes, but not the request/timeout pair, the event object 28 bits 0x100/0x200, or the ops table built by 0x7E519D8C.

The strong areas were the curated D5 reads (SYSFMEM, DCF, TAKE state tables, live-bulb callbacks, mcon hooks). There every row checked was right, apart from a small condition slip in F019.
