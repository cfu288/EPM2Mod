# Coverage review, round 8, batch 4 (F061–F080)

**Method.** For each function I first wrote a prediction from the map only. I used the regions table in `docs/firmware-map.md`, `modules.tsv`, sections 13b, 13d, 14a, 15a and 16b/16c/16e, and the 16x row for the address. Then I read the code with `tools/fwmap.py` and `tools/disasm.py`, and I read vtables, jump tables and data tables directly from block 0. None of the 20 functions falls inside a `modules.tsv` range, except F078 (`CAvpiAsoAudioSource.cpp`, 0x7EEA132E–0x7EEA1A23). DB `suspect` = 0 for all 20.

**Name sources** (only to name things, not as map evidence):
- the D1 Ss tables (decoded by `ss.py`);
- the OlyApi name table `scratchpad/d4/app/apinames.pkl`. The API id was read from the constant inside each vtable slot target.

**Scratch.** `/tmp/scratch/04b1caa0-6975-4677-98e3-f42129671871/scratchpad/coverage8/batch4/` holds:
- the `fwmap fn --dis` dumps (`0x*.txt`);
- `rd.py` (a raw block-0 reader), `ss.py` (Ss descriptor decoder) and `api.py` (OlyApi slot → API id), all copied from round 7;
- `merged.py`, which tests the 16b "merged vtable methods" rows against the function's own jump tables (see "Other map errors", item 1).

**Labels.** "Verified" = read in the code or the bytes. "Inferred" = from names, strings, call position or layout.

## CONTRADICTED items, with proof

**F063, 16b row `0x7EDA116A … also holds 11 more vtable method(s) merged by fwmap: 0x7EDA1210 = slot 0; 0x7EDA1214 = slot 2; 0x7EDA1218 = slot 1; 0x7EDA121C = slot 3; …`** (row V/I = I). There is no vtable. These addresses are the case labels of F063's own switch:
1. F063 loads `mov 0x7EFD29DC,a0` at 0x7EDA1203, indexes it with (RAM 0x602BD11C − 3) × 4 and does `jmp (a0)` at 0x7EDA120E.
2. The words at 0x7EFD29DC–0x7EFD2A04 are 0x7EDA1210, 0x7EDA1218, 0x7EDA1214, 0x7EDA121C, 0x7EDA1220, …, 0x7EDA1238. The row's "slot" numbers are the indexes in this table (0x7EDA1214 = index 2, 0x7EDA1218 = index 1).
3. Each target is a 4-B case: `mov N,d2; bra 0x7EDA123A` (N = 2, 3, 5, …, 13), which jumps back to F063's own epilogue. They are not methods.

The same false positive is in other 16b rows. `merged.py` found 17 of the 226 rows with slot lists where every listed target is in a table that the row's own function loads; 7 of them contain `jmp (aN)`: 0x7ECE3DCD, 0x7ED168CD, 0x7EDA0CDD, 0x7EDA0F5A, 0x7EDA116A, 0x7EDED398 and 0x7EDED561. I checked 0x7EDA0F5A (the same switch shape, table → 0x7EDA1007/0x7EDA100B/0x7EDA100F) and 0x7EDED398 (`mov 0x7EFE5824,a0; mov (d0,a0),a1; jmp (a1)`; "slots" 32/38/40) by hand. The other 10 of the 17 have no indirect jump and are probably ctors that load their own vtable, so they can be correct.

## Other map errors and tool notes found next to the batch

1. **16b "merged vtable methods" rule takes switch tables for vtables** (F063; at least 3 rows confirmed, 7 probable). The rule should require that the table is stored as a vtable (by a ctor) or is not the operand of a `jmp (aN)` in the same function.
2. **16b row for F064: the merge note is wrong.** It says that no pointer to 0x7EDA7329 was found. Word 0x7EFD30E8 of the SS_MENU_LV exit table points to it (SS4 state 7 exit). The rows for merged code after an exit do not check the Ss entry and exit tables.
3. **16e family edge "float internals 0x7EE1B436–0x7EE1E8DF"** includes the integer texture-name hash insert F068 (0x7EE1E87E–0x7EE1E8DF). The edge should be at most 0x7EE1E87D.
4. **Ss handler rows that return a value "from locals"** (F064) still do not resolve the destination when it is read from a CCommon field (+128, setter 0x7ED0195A). This is the same gap as in round 7.
5. **Not in the map:** the per-mode operation-id tables 0x7EFC48BC (F062; "2000 = none"); the DPS step variable RAM 0x602BD11C and its 15-way action switch (F063); the LV-hint item records RAM 0x602BD64C (F065); the GL texture hash (F068); the AVPI payload class vt 0x7F02FD38 (F077); the Audio Source events 0x0B210004/0x0B210008 (F078); the Video Decode limits 1920 × 1088 (F079).
6. **Observation (not an error):** the DMP GL `glGetTexGen*OES` functions accept coord 0x8000, not 0x8D60 (GL_TEXTURE_GEN_STR_OES in the Khronos headers) (F069).

## Where the map is weakest

1. **AVPI plug-in slots and framework classes (0x7EE90235–0x7EECE318).** 16e wires the plug-in slots correctly (F078 slot 48, F079 slot 10), but there is no slot dictionary for the 65-slot plug-in interface, so no slot has a role (deliver captured block, accept a format). The framework classes without names (the timer list type 0x0C03, the payload class vt 0x7F02FD38) get only callers and error codes (F076, F077).
2. **3D engine and GL helpers.** The P/C rows give only the callees and soft-float counts. The roles are short and easy to read: mip-level size (F070), a textured-quad blit (F071), scissor (F072), the texture hash insert (F068) and the GL state free (F067). A rule that names a function after its single back-end GL callee (scissor, viewport, draw) would cover F072 and part of F071.

4. **GUI helper code outside Ss tables.** Rows for helpers list the callee effects (ModeCheck, DM blocks) but not the purpose (F062, F065). The structural tags are not reliable: one in three batch rows in the GUI area had a false tool note (F063 merged methods, F064 merge note).
5. **Overlay B ADJSLF.** The rows are context only (F080). The ADJSLF work area (RAM 0xA06E1734, more than 512 KB) is not described.
