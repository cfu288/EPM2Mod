# Coverage review, round 5, batch 4 (F061–F080)

**Method.** For each function I first wrote a prediction from the map only. The map sources were the regions table in `docs/firmware-map.md`, `modules.tsv`, and sections 01, 07-settings.tsv, 10e, 10f, 11, 13b, 13d, 14a, 14e, 15a (md and tsv) and 15d. Then I read the code with `tools/fwmap.py` and `tools/disasm.py`, and I read vtables, descriptor and data tables directly from block 0.

**Name sources.** I used these only to name things, not as map evidence:
- the D1 Ss handler table `scratchpad/d1/gui-toolkit/ss/handlers.tsv`, for SS, state and event names;
- `scratchpad/d1/gui-toolkit/panels.txt`, for panel vtables;
- `out/lang/101_1600.en.tsv`, for string ids;
- the `Class::method` name strings, for OlyApi methods. Slot vt+N is the (N/4+1)-th name. I checked this on PlaySound vt+16 = `setVolume`, which carries the log string "setVolume not maintenance".

**Scratch.** `/tmp/scratch/04b1caa0-6975-4677-98e3-f42129671871/scratchpad/coverage5/batch4/`. It holds the per-function `fwmap fn --dis` dumps, `rd.py` (a raw block-0 reader), `mapgrep.py` (an address/range grep over the map) and `owner.py` (finds the function that contains an address and looks up its Ss handler rows).

**Labels.** "Verified" = read in the code or bytes. "Inferred" = from names, strings or layout.

## CONTRADICTED map claims (found next to the batch functions)

No batch function contradicts its own map row. These four claims on neighbouring code are wrong.

1. **10f §4.2 (and 13d §4 line 231): CA misc sub-app table, row format and event ids.**
   - The map says the table at 0x7EED9400 holds `{state, next, handler, event}` rows, that 0x0600000B → `startSelfAdjustMenuSubAppStateMisc` 0x7ECE067B and 0x0600000A → VerCheck 0x7ECE0653, and that 0x7ECD6728 maps param 11 → 0x0600000B and param 12 → 0x0600000A. 13d says the VERCHK event is 0x0600000A.
   - **Row format.** The state descriptor 0x7EED9DBC = {0x2000, **0x7EED93EC**, 11}, then {0x2001, 0x7EED949C, 1}, {0x2002, 0x7EED94AC, 5}…. The rows therefore start at 0x7EED93EC and tile exactly (11 × 16 B). Each row is **`{event, flag, next_state, handler}`**: field 2 holds the state ids 0x2001–0x2008.
   - **Event → handler.** Read this way, the rows are 0x06000009 → VerCheck 0x7ECE0653 (next 0x2006), **0x0600000A → SelfAdjust 0x7ECE067B** (next 0x2007), and **0x0600000B → `startFirmupSubAppStateMisc` 0x7ECE06C0** (next 0x2008).
   - **Param → event.** The jump table of 0x7ECD6728 is indexed by param − 1 and gives param 11 → 0x0600000A, 12 → 0x06000009, 13 → 0x0600000B. The names come from 0x7ECD68D8 (same indexing): 11 = CAM_MISC_SELF_ADJUST, 12 = CAM_MISC_VERCHK_MENU, 13 = CAM_MISC_FIRMUP.
   - **Effect.** The map's param → handler result happens to be right, but every event id it gives is wrong. VERCHK is **0x06000009**, not 0x0600000A, and FIRMUP (0x0600000B) is missing. The PC sub-app tables (F061) use the same format.
2. **13d §4 line 232: "code 11 → CA event 0x0400000B `GUI_START_SHOOTING_SERVICE`".**
   - The name table 0x7EEEFFD0 is a list of `{id, char*}` pairs. Its user, 0x7ECE5465 in 0x7ECE5383, is a strcmp name→id lookup. In it, id 0x0A = `GUI_START_SHOOTING_SERVICE`, **0x0B = `GUI_END_MENU`** and 0x0C = `GUI_END_LV_CONTROL`. The table 0x7EEEBB28 maps code 11 → 0x0400000B.
   - The batch confirms that the table is keyed by code: the ART-menu exit F069 posts code 6 = `GUI_END_ART_SELECT`, and the LV exits F068/F069 post code 12 = `GUI_END_LV_CONTROL`.
   - So the Firmware item posts **GUI_END_MENU** with info 12, not START_SHOOTING_SERVICE (verified table; reading the name by code is inferred, but it fits 3 of 3 checks).
3. **10e §: "`startPc` 0x7ECE09FC".** 0x7ECE09FC logs `connect`. `startPc` is 0x7ECE0F29 (its string), and 0x7ECE0F29 calls 0x7ECE09FC. 10e also calls the 0x0900001x values "GUI events". They are CA sub-app events in PC state 0x6000 (descriptor 0x7EEDAD70).
4. **13d §4.2: SS_SELFADJ handler code "0x7EDBEE1C–0x7EDC0097".** 0x7EDC0097 is the start of the state-9 entry (F070, 38 B). The range ends at **0x7EDC00BC**, and SS_SPC starts at 0x7EDC00BD.

## Where the map is weakest

1. **Individual methods of GUI classes.**
   - The map names the class or panel for every GUI function in the batch (panels 14, 22 and 24, the screen class, the USB-connect screen, viewer id 10), but it gives no slot roles past the root/widget tables.
   - Panel slot 91 (post-create init, called from CreatePanel), slot 106 (child builder) and screen slots 125–132 (indexed attribute arrays) are not mapped.
   - The controller-class row of 13d §1 leaves out **CPlayMovie** (playback volume, slide show), although its strings are there.
2. **Ss handler rows.** The 15a ss-state rows give only the entry function and the panel. All 5 handler functions (F066–F069 and F063's callers) needed the D1 handler table to name the event, and their logic (DPS failure classes, BT PIN send, Fn-key assignment value 44, CA codes) is absent. The map also has no table of PostEventToCA codes. The name table 0x7EEEFFD0 would give one, and it would fix item 2 above.
3. **CA_MAIN sub-app tables.** The `{event, flag, next, handler}` tables and their state descriptors (misc 0x7EED9DA0…, PC 0x7EEDAD70…) are not documented as a format, and the one place that uses them (10f §4.2) misreads them. This is the most error-prone area found.
4. **3D engine and C3D internals.** Below the loader table and the class tree, the map has no function roles: the MT sub-parsers, the matrix palette, list serialisers. 14a's own "inferred" roles are not tied to functions.
5. **AVPI framework classes and overlay-B utility code.** For AVPI 0x7EE90235–0x7EE9C331, 13b says it does not map class roles. Overlay B 0x7F09xxxx (TPC PTP/MTP utilities) and the ADJSLF sequences have only region rows. The ADJSLF "UnitCodeCam" sequence, which sets PRM_DESTINATION_AREA and **PRM_MODE_SHIPS_ENABLE = 1**, bears directly on the ADJSLF gate in 10f but is not in the map.
6. **Tool splits.** fwmap merges 1–10 small functions or stubs into the function before them: F062 includes the slot-130 getter, and F066 includes 10 separate Ss action stubs. As 14e §5 D says, function sizes in this area are not reliable.
