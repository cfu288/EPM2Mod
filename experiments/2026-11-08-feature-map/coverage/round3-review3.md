## Map claims that the code contradicts

**C1. The event-TSV owner of block 7591–7611 is "CmpSht_ShootingComponent_NEW (next class)" (13c-event-ids.tsv, all 21 rows).** No function verdict depends on it, but the claim is false.
- **Senders.** The ctors 0x7EB79D60–0x7EB79F94 are called by 75-byte observer updates at 0x7EB3D9FB–0x7EB3DEAC (e.g. 0x7EB3DC6E → 7604, 0x7EB3DA61 → 7611; vtable words such as 0x7EC79354). The ctors of those observer members (0x7EB3DA46, 0x7EB3DBED, 0x7EB3DC53, 0x7EB3DCB9, 0x7EB3DD50, 0x7EB3DDB6, 0x7EB3DE21, 0x7EB3DE8C, each → 0x7EB85D67) have one caller: the **Cmp_PlayComponentBase ctor 0x7EB0A5E7**.
- **Receivers.** The 38 play/edit running handlers (F041 family) and 0x7EB0F0D2.
- **Names in code.** 7604 is handled by `Cmp_PlaySingleComponentBase rcv [evTraCmpPly_NotifySelectDisplayExecuteEnd]` 0x7EB109D3. CmpEAsp logs `save_start_enter rcv[evTraCmpPly_NotifySelectExecuteEnd]` 0x7EC5C0DE.
- **So** the block is the `evTraCmpPly_*` play-component notification package, not shooting events. The "next class" heuristic failed because the package's events are linked just before CmpSht.
- The same heuristic gives 3613 (block 3611–3623) to Com_ManagersSubTransition, but the only users of 3613 are 5 PictBridge functions (F042). It is probably wrong too; I did not check the other ids in that block.

**Imprecise (not counted):**

## Where the map is weakest (from this batch)

1. **The play-component notification protocol.** Cmp_PlayComponentBase owns 8 observer classes (code 0x7EB3D99F–~0x7EB3DEF7, between CmpPMov and the CmpPPnr observers in link order). They relay CapPls/CapImg notifications as `evTraCmpPly_*` (7591–7611); each id is tested in 38 components. The map has no names, senders or meanings for them, and the TSV gives them the wrong owner (C1). The 1.5 KB running handler, copied 38 times, is mapped only for its CM ids.
2. **Per-class charts below the class name.** The Shutdown component chart (stop the capabilities one by one, state 11, event 5761), the PictBridge states (state 35, request 3613, NACK by the id of 13810) and the LightBox post-erase 7609/7610 handshake are not mapped. The map names these classes and nothing more.
3. **Com_ManagersSubTransition internals.** The accepted-request prototype list at +144 is not mapped: the slot-42 hook fills it (F048), and the dtor and stop paths clear it (F049). This list is how a CmpSts controller declares the `evTraReqSht*` requests it serves.
4. **GUI methods without strings.** The touch-action dispatcher (F053), layer-ordered child insertion (F054), DC accessors outside the DC range (F056) and unnamed-panel helpers (F057) can be placed but not explained. For Ss functions without a `doCmd` string (F059), the map cannot say which screen a state is: no per-SS state-name table is decoded, although 13d notes that one exists for debug.
5. **Device classes in `Dev*` part 1.** DevLed (34 LED types, one instance per type, `api_led_*` wrappers, 6 observer lists) appears only as the word "LED". The same probably holds for the other part-1 devices that 13c lists without addresses.
