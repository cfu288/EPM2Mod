## CONTRADICTED items

None of the 20 batch functions contradicts a map statement about itself. Three map claims elsewhere are weakened or wrong:

1. **"IMG_PRECON is pixel-defect correction, not generic pre-conditioning"** (13a §3, firmware-map D1 note, feature inventory "Pixel Mapping"). This is overstated. IMG_PRECON command 4 (0x7E55FA0A → 0x7E580A54(0), then (1) if the first call fails) loads prm 0xAC51/0xAC61/0xAC71/0xAC81 (65-point tables, 0xAC81 tagged `STATE_LENS`). Through F009 it computes channel-ratio gains ×128 and writes them back to prm (V). The task also runs a colour/WB-type calibration, not only defect correction. The handler 0x7E580A54 is outside the IMG range the map gives (0x7E544AA9–~0x7E576D58).
2. **13e §1 row "0x7E6FE251–0x7E6FE43F language-list init"** (I role). The first function, 0x7E6FE251, is the **mcon module init**. Its only caller is Usr0 (0x7E503DD4), and it calls 15 functions across the whole module (0x7E706905, 0x7E70097E, 0x7E6FF6C2, 0x7E7002E4, 0x7E6FFE2C, 0x7E7012AF, 0x7E701178…). The language-list code is only 0x7E6FE2C6–0x7E6FE43F (`Warning Language error`, `AllocMemory error LanguageInfo`).
3. **"The mirror code is a stub left over from DSLR code"** (03 §2, inferred). This is weakened, not disproved. MI open 0x7E642398 opens the MEC timing unit (0x7E51783A → 0x7E50F8F3, the same entry the shutter code uses) and creates cam timers 13–16. It is driven by 7 event-callback sequences (F016) that send command lists 0x94/0x97/0x98/0x10093. On a mirrorless body the "mirror down" phases probably run the shutter close/charge (I). The `mirror_dummy_post_*_err` strings may cover only part of the module.

## Where the map is weakest (from this batch)

1. **Stringless code between named modules has no label.**
   - The utility library 0x7E507000–0x7E508F81 (F004): heap alloc/free 0x7E507325/0x7E507333, a second `memcpy` 0x7E5081FA (380 callers), a `memset` 0x7E5082B6 (667 callers), `strlen` 0x7E508346, clock 0x7E5083B5, and the calendar/date-time formatter. 13a covers only the C runtime up to 0x7E501C5A; 13f starts UI/keys at 0x7E508F82.
   - The gap 0x7E579A80–0x7E58204C between `buff` and TAKE_MAIN (F009), which holds IMG_PRECON's command-4 handler.
   - Camera-core blocks 0x7E635F15–0x7E63790C (F015, a sensor-mode parameter builder) and 0x7E640F00–0x7E642324 (F016's mirror sequences; also the cam heap 0x7E641C2E/0x7E641D60 with 203/188 callers and its `Used Block` dump). modules.tsv places them in `cam_ev.c` / `cam_imgdev.c` by position only, and the code does not fit those files.
2. **Driver and service internals stop at the unit name.** The batch hit the EMS result format (F002), IOE SIO callbacks (F003), the MEC MAG/MOT command layer (F006), the external-strobe serial wait (F013), DCF file-type scanning with MP4 support (F010) and the exFAT formatter (F011). The map names each unit, but not these roles.
3. **Algorithms without strings:** the SDET scene decisions (F017; scene ids 3 and 23 are not tied to names), and the colour/WB maths reached from IMG_PRECON (F009).
4. **Callbacks reached only by pointer** (F003, F006, F016 have 0 callers; F014 is reached through a command table). The database marks their address loads as "raw bytes … unaligned" in `xref`. This is not a mis-split, but caller-based tracing misses these functions.
